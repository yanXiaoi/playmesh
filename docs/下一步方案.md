## 1. 总体结论

1. 游戏分享页的服务器名称统一使用 App 本地配置的源名称，源声明名称只在源详情中展示。
2. 游戏包导出文件名统一为 `游戏名称-v游戏版本.zip`，每次分享前清理旧导出文件，并改为流式压缩以控制内存。
3. 在线游戏库拆分为“首页”和“搜索”。首页一个源一个区域且不跨源去重；搜索按 `gameId + 发布者` 聚合，每个源只贡献自己的最新版本。
4. 游戏包根目录支持 `icon.png`；在线 Catalog 通过 `icon` 字段提供同源图片转发地址。
5. 游戏源配置支持详情页，区分本地配置名称和源官方声明。
6. go-server 增加邮箱账号、登录注册、可选邮箱验证、展示名称、上传密钥和个人游戏包管理。
7. 所有游戏 `author` 字段的对外标签改为“发布者”，底层字段名不变。
8. 开发者工作区增加“发布”入口，可选择多个已配置上传密钥的源逐源提交审核。
9. `gameId` 由首次上传账号取得所有权，存在任一版本期间其他账号上传同 ID 必须拒绝；最后一个版本删除后释放。
10. go-server 和 App 自身暴露的游戏源都统一使用 `publicURL?token=xxxx` 分享、扫码和导入；导入前必须成功请求 `/apps/info`。
11. App 用户可选择图片头像；多人会话中由权威主机保存到固定保留 Bucket。
12. SDK 所有玩家信息都在 `nickname` 同级返回 `avatar`，中文含义为“头像”。
13. App 将游戏最近打开时间和启动次数统一保存为可扩展的 gameId 统计对象；本地和在线搜索热度都使用本机 `launchCount` 并倒序排列。
14. go-server 增加“允许用户注册”开关；关闭时隐藏公共登录/注册入口并拒绝新注册，但已有用户仍可通过登录路径正常登录。
15. go-server 管理员可对已审核游戏执行上架/下架；游戏所有者可物理删除自己的已下架版本。
16. 每个游戏源对同一 gameId 只公开当前最新版本，旧版本不进入展示或下载渠道。
17. 用户每次打开游戏库时后台检查更新；同 gameId、同发布者且源版本更高时提示升级，并展示版本和可用源。
18. 开发者工作区或 go-server 用户门户上传游戏时，新版本必须严格高于该 gameId 当前最高版本。
19. AI 默认提示词严格以 `assets/playmesh-library/public/developer/prompts` 为唯一真源；每次发行打包都必须包含该目录的最新模板，并通过产物哈希校验阻止旧模板进入安装包。
20. 本地游戏库增加一个统一搜索框，同时匹配发布者、名称、gameId、描述、版本和标签，不拆分为多个条件输入。
21. 使用 `frontend-design` 和 `web-design-guidelines` 对 App 现有 UI 与开发者工作区 HTML 做纯表现层重设计；首页先展示游戏库，其次在线游戏库，其他入口最后展示。
22. 最终 UI 阶段为 App、开发者工作区和 go-server Web 增加可配置国际化、主题与系统/日间/夜间切换；API 返回不参与翻译。
23. 正式开发前必须阅读仓库开发文档并按领域形成约束清单；验证必须完整，所有正式测试、分析和构建命令均先申请沙箱外权限并在沙箱外串行执行。
24. App 全部 UI 及其 WebView 内平台 UI 都必须支持键盘和 Android TV 遥控器操作，并完整适配 TV、平板、手机和电脑。
25. Game SDK 向权威主机新增一键打开现有分享界面的能力；游戏运行时 FPS、展开工具条、菜单列表及其他平台覆盖层默认全部关闭。
26. 本文编号只表示需求索引，不要求按编号顺序实现；执行者应根据依赖和共享改动自行组织链路，一次处理同一模块的相关需求，避免重复生成、迁移、改版和回归。

## 2. 术语与全局规则

### 2.1 关键术语

| 术语 | 定义 |
| --- | --- |
| 本地源名称 | 用户在当前 App 中为某个游戏源配置的名称。 |
| 源官方名称 | `/apps/info` 返回的 `name`，只用于详情和辅助识别。 |
| 读取 Token | 请求 `/apps/info`、`/apps/list`、`/apps/icon`、`/apps/download` 的凭据，可随源链接分享。 |
| 上传密钥 | go-server 用户为 App 发布配置的写入凭据，不得进入二维码、源链接或 Catalog 返回。 |
| 游戏 offer | 一个确定的 `sourceId + gameId + version` 下载项。 |
| 发布者 | 游戏 `author` 字段的对外展示名称。 |
| 建造者 | 游戏源声明 `author` 在源详情中的展示名称。 |
| 会话头像 | App 玩家进入多人会话后，由权威主机提供的同源图片资源。 |
| AI 默认提示词 | 仓库 `assets/playmesh-library/public/developer/prompts` 中登记并随 App 打包的模板内容；不包含用户本地自定义覆盖。 |
| UI 国际化 | 仅翻译 App、开发者工作区和 go-server Web 的界面文案；API 契约、用户内容和游戏源内容保持原值。 |
| 语言清单 | 声明可用语言、默认语言、回退语言和各 UI 词典文件的外部配置；运行时代码不得维护固定语言数组。 |
| 开发文档门禁 | 编码前阅读通用规范、环境、版本基线及当前领域开发约定，并把适用约束转成实施检查项。 |
| 正式验证 | 用仓库规定的固定工具链在沙箱外执行的格式、分析、测试、契约检查、端到端和发行构建验证。 |
| 平台 UI | 由 Playmesh/App/SDK 注入并控制的界面，包括 Flutter 页面、覆盖层、WebView 工具、悬浮球、菜单、弹窗和状态控件；不包含游戏作者自行实现的游戏内容。 |
| TV 键盘操作 | 使用 Android TV 遥控器方向键、确认键、返回键、菜单键及等价键盘按键完成全部平台 UI 操作。 |
| 权威主机分享能力 | `openSharePanel()` 只打开既有分享界面且不返回数据；App-only 的当前本机 Authority/standalone host 可另用 `playmesh.app.lan.getShareLinks()` 读取统一快照中的完整邀请 URL 与二维码。 |
| 实施依赖图 | 以单一事实源、数据契约、共享文件、生成链和验证边界组织的工作图；用于决定实际批次，不受 FR 编号顺序约束。 |

### 2.2 全局不变量

1. 每个源对同一 gameId 最多返回一个最新版本 offer；不同源各自的最新版本必须可追溯、可选择、可下载。
2. 本地源名称的界面优先级高于源官方名称，官方改名不得覆盖用户本地命名。
3. 游戏所有权只根据 go-server 账号 ID 判断，不使用邮箱、显示名称或包内 `author`。
4. 已审核且上架的包不能直接删除；游戏所有者下架后可物理删除自己的版本。
5. 待审核包允许用户物理删除，并立即退出审核队列。
6. 扫码和手工输入必须调用同一套源导入函数。
7. 上传密钥永不进入二维码、分享链接、网页 JavaScript、日志或错误详情。
8. SDK 中所有 `PlaymeshPlayer` 结构必须具有一致的 `avatar` 字段。
9. HTML 玩家不能上传头像，只能使用 `setNickname` 修改昵称。
10. 所有以 `_sys-` 开头的 Bucket 都是平台保留 Bucket，游戏代码不得创建、占用、上传或清空。
11. 本轮允许破坏性更新，不实现旧配置、旧 API、旧二维码、旧数据库或旧本地元数据的兼容读取。
12. AI 默认提示词正文不得在 Dart、JavaScript、构建脚本或其他资源目录中复制；运行时默认值、恢复默认和发行包只能读取唯一模板目录。
13. 本地游戏库搜索只使用一个输入框；搜索不得发起网络请求或修改游戏、统计及更新状态。
14. UI 重设计不得改变现有路由、DOM ID、Developer Gateway、SDK、API、数据模型和业务状态机。
15. 支持的语言、默认语言和回退链必须由配置与词典资源决定；不得在 Dart、JavaScript、Go 或 HTML 中写死语言选项和语言判断分支。
16. `docs/下一步方案.md` 不能替代工程开发规范；实现时必须以当前仓库开发文档和最近版本日志为事实基线。
17. 沙箱内测试结果不作为本轮正式验收结论；所有正式测试、静态分析、原生工具和平台构建必须先请求沙箱外授权并记录真实命令与结果。
18. App 平台 UI 不得依赖触摸、鼠标悬停、拖拽或手势作为唯一操作方式；每个功能必须存在可见且可聚焦的键盘/遥控器路径。
19. TV、平板、手机和电脑共享业务逻辑，只通过响应式布局、输入映射、焦点策略和信息密度适配，不建立设备专用业务分支。
20. 游戏脚本不得从 UI、DOM、日志或自行拼接的旁路取得分享凭据；但 App-only 的当前
    本机 Authority/standalone host 经 `playmesh.app.lan.getShareLinks()` 获得完整邀请
    URL 与二维码是明确授权。源上传密钥始终不可读，平台也不得自动记录或持久化分享结果。
21. 每次进入或重新创建游戏运行页时，除收起状态的工具悬浮球外，FPS、展开工具条、更多菜单、信息、日志、分享和调试覆盖层全部初始化为关闭。
22. 同一事实源或共享模块的相关需求应在一个实施批次内完成；不得按 FR 编号逐项重复修改相同 schema、注册表、页面、生成物和版本常量。

### 2.3 破坏性升级策略

本轮按全量破坏性版本处理：

1. 不实现双版本读取、双写、旧字段别名、旧路由转发或旧协议降级。
2. Catalog 只支持 `2.0.0`，其他版本在探测阶段直接拒绝。
3. 旧 `playmesh://catalog-source` 二维码和分离 Host/Token 导入格式直接拒绝。
4. App 旧源配置、旧用户资料和旧游戏库元数据不迁移；检测到旧格式后隔离原文件并创建新格式。
5. go-server 旧数据库不自动迁移。Schema 版本不匹配时拒绝启动，管理员备份后使用新数据库重新部署。
6. 旧匿名上传记录、旧审核记录和旧 gameId 不设计绑定或兼容流程。
7. `main.json.icon` 旧语义移除，只认根目录可选 `icon.png`。
8. 不保留 Catalog 1.4“缺少 version 时下载最新版本”的兼容行为。
9. SDK 和 App Bridge 以本次新契约重新生成，依赖旧返回结构的游戏需要重新构建。
10. 发布说明必须明确列出需重新配置游戏源、重新登录/注册、重建 go-server 数据库和重新生成二维码。

### 2.4 统一版本格式

App、游戏和协议版本统一使用三段式语义版本：

```text
MAJOR.MINOR.PATCH
```

约束：

1. 必须精确包含三个非负十进制整数，例如 `2.3.1`。
2. 除数字和两个点外不允许其他字符。
3. 不允许 `v2.3.1`、`2.3`、`2.3.1-beta`、`2.3.1+5` 或前后空白。
4. 每段除单独的 `0` 外不允许前导零。
5. Manifest `version`、`sdkVersion`、`appSdkVersion`，Catalog API 版本、上传协议版本和 Relay 协议版本都遵循相同格式。
6. App 的构建号继续作为独立构建元数据管理，不进入游戏版本比较。
7. 比较顺序依次按 MAJOR、MINOR、PATCH 数值比较，不按字符串排序。
8. 导出文件名中的 `-v2.3.1.zip` 仅是文件名展示，Manifest 中仍保存 `2.3.1`。

## 3. 目标界面与交互

### 3.1 在线游戏库

顶部使用两个页签：

- `首页`
- `搜索`

AppBar 保留下载队列和游戏源配置图标。

#### 首页

首页只请求：

```text
source.enabled == true && source.showOnHome == true
```

每个源单独形成一个全宽区域，区域顺序按本地源配置顺序排列。

每个区域具有独立状态：

| 状态 | 展示 |
| --- | --- |
| 加载中 | 保留源标题，显示固定高度加载状态。 |
| 有数据 | 按源返回顺序展示，不与其他源合并或去重。 |
| 空数据 | 保留区域，显示“此游戏源暂无数据”。 |
| 请求失败 | 显示源内错误和“重试”按钮，不影响其他源。 |
| 已禁用或关闭首页展示 | 首页不请求、不显示。 |

首页不得按 `gameId`、名称、版本、URL 或哈希去重。

#### 搜索

搜索请求所有 `enabled=true` 的源，不受“首页展示”开关影响。

展示层级：

```text
游戏摘要
  -> 版本列表
     -> 当前版本的全部下载源
        -> 选择源并下载
```

一级搜索结果按 `gameId + 发布者` 聚合。只有 `gameId` 和发布者都相同的结果才显示为一个摘要；同一 `gameId` 只要发布者不同，就必须单独显示摘要。

摘要仅展示：

- 图标
- 名称
- 介绍
- 发布者
- 热度（本机启动次数）

点击摘要后显示各来源“当前最新版本”形成的版本集合；点击版本后显示最新版本等于该版本的全部源。任何源的历史版本都不进入此流程。

聚合只改变界面层级，不得删除原始 offer：

```text
AggregatedGameResult
  gameId
  publisher
  groupKey = gameId + publisherKey
  heat = localUsage[gameId].launchCount ?? 0
  representative
  versions[]
    version
    offers[]  // 每一个源的返回均保留
```

发布者聚合规则：

1. `publisherKey` 默认使用 Catalog `author` 去除首尾空白后的完整字符串。
2. 发布者名称精确比较，不做大小写折叠、别名合并或模糊匹配。
3. `author` 缺失或为空时，使用 `sourceId` 作为隔离键，避免将不同来源的未知发布者错误合并。
4. 同组中保留各源当前最新版本的 offer；同一源若异常返回多个版本，视为协议错误，不展示其历史项。
5. 此规则只负责搜索展示，不参与 go-server 的游戏所有权判断。

代表信息默认取该聚合组内的最高语义版本；同版本存在冲突时，按本地源配置顺序选择代表项。

搜索排序规则：

1. `heat` 读取 App 本地 `game-library.json` 中该 `gameId` 的 `launchCount`，未记录时为 0。
2. 本地统计按 gameId 保存，因此同一 gameId 的不同发布者摘要使用相同本机启动次数。
3. 所有一级搜索摘要按 `heat` 倒序排列，值越大越靠前。
4. 热度相同时，依次按 `lastOpenedAt` 倒序、组内最高语义版本倒序、游戏名称正序、`groupKey` 正序，确保顺序稳定。
5. 游戏每次进入实际运行页面时原子增加一次启动次数并更新最近打开时间。
6. 本地统计更新或某个源加载更多后，重新计算完整聚合结果并排序，不得只排序当前可见局部列表。

下载任务键必须包含：

```text
sourceId + gameId + version
```

不同源或不同版本可以同时进入下载队列。

### 3.2 本地游戏库搜索与后台更新检查

#### 统一搜索框

本地游戏库标题下方只显示一个搜索框：

```text
搜索游戏名称、发布者、ID 或介绍
```

交互规则：

1. 输入后在本机缓存中实时过滤，使用 200 ms 防抖；按 Enter 立即执行当前查询。
2. 搜索框左侧使用搜索图标，存在输入时右侧显示清除图标；不再增加发布者、名称或标签等独立筛选框。
3. 空查询展示完整本地游戏库；清除后恢复原列表和原滚动起点。
4. 搜索结果区域显示匹配数量；无结果时保留搜索框并显示“未找到匹配游戏”，提供“清除搜索”操作。
5. 扫描、导入、删除或升级导致游戏列表变化时，以当前查询自动重新过滤，不清空用户输入。
6. 搜索只处理本地已安装游戏，不请求在线源，也不影响后台更新检查。
7. 桌面端可在进入游戏库后使用 `Ctrl/Cmd + F` 聚焦该唯一搜索框；移动端不自动弹出键盘。

匹配字段：

- 发布者：`GameSummary.author`，界面标签显示“发布者”。
- 名称：`GameSummary.name`。
- 游戏 ID：`GameSummary.id`。
- 介绍：`GameSummary.description`。
- 游戏版本：`GameSummary.version`。
- 标签：`GameSummary.tags`。

匹配算法：

1. 查询去除首尾空白并把连续空白折叠为一个分隔符。
2. 拉丁字符按不区分大小写匹配；中文及其他字符按原字符子串匹配。
3. 查询按空白拆成多个关键词；每个关键词可以命中任意字段，但所有关键词都必须命中。
4. 不做拼音、同义词、模糊编辑距离或远程补全，避免不可解释的匹配结果。
5. 结果按本地搜索热度规则排序：`launchCount`、`lastOpenedAt`、版本、名称、gameId。

#### 后台更新检查

用户每次进入本地游戏库页面时：

1. 立即使用本地缓存渲染游戏列表，不等待网络。
2. 后台查询全部 `enabled=true` 的游戏源，`showOnHome` 不影响更新检查。
3. 同一次页面打开只启动一个检查任务；重复 rebuild 复用正在进行的任务。
4. 单个源失败不影响其他源，错误只进入本次检查摘要。

升级候选必须同时满足：

```text
offer.gameId == installed.gameId
&& offer.publisherKey == installed.publisher.trim()
&& semver(offer.version) > semver(installed.version)
```

发布者为空、不同或版本无法解析时不生成升级候选。

界面展示：

- AppBar 显示“可更新 N 项”入口。
- 对应游戏行显示“可升级”状态。
- 更新详情显示当前版本、目标版本、发布者和提供该版本的全部源。
- 源名称使用 App 本地配置名称，同时显示版本号。
- 多个源提供不同更高版本时按语义版本倒序分组；默认选中最高版本。
- 同版本存在多个源时全部列出，由用户选择下载源。
- 没有更新时不弹提示，只更新最近检查状态。

快速升级：

1. 用户选择目标版本和源。
2. 下载该源当前最新 offer。
3. 安装前再次校验 gameId、发布者和版本严格高于当前安装版本。
4. 使用现有不可信 ZIP 校验和原子安装流程替换游戏程序文件。
5. 游戏数据目录、使用统计和用户动态数据不得随包替换删除。
6. 成功后重新扫描游戏库、清除更新提示并显示新版本。
7. 下载失败或包校验失败时保留当前安装版本，可切换其他源重试。

### 3.5 go-server 用户门户

公开页面保留已上架游戏浏览，移除匿名邮箱上传入口。

公共导航根据 `allow_user_registration` 展示账号入口：

| 配置 | 公共导航 | `/login` | `/register` |
| --- | --- | --- | --- |
| `true` | 显示“登录 / 注册” | 正常登录 | 正常注册 |
| `false` | 不显示登录和注册入口 | 直接访问仍可正常登录 | 页面可访问，但显示“当前未开放注册”，提交注册被拒绝 |

关闭注册不得删除、禁用或退出已有账号，也不得影响登录、邮箱验证、个人后台和上传密钥。

用户门户包含：

- 注册
- 登录
- 邮箱验证提示和重发
- 账号设置
- 对外展示名称
- 上传密钥管理
- 登录用户上传游戏包
- 我的游戏包

网页上传区显示 gameId、包内版本和该游戏当前最高版本。相同或更低版本在服务端拒绝后，页面提示修改 `main.json.version` 再重新上传。

“我的游戏包”按游戏和版本展示：

- 游戏名称
- 版本
- 审核状态
- 公开状态
- 审核说明
- 更新时间
- 可执行操作

不同状态允许的操作：

| 状态 | 用户操作 |
| --- | --- |
| pending | 删除并取消审核，物理删除 ZIP。 |
| approved + published | 下架，不删除文件。 |
| approved + unpublished | 上架，或删除版本及其包文件。 |
| rejected | 查看原因并删除记录和文件。 |

游戏卡片可提供“删除全部已下架版本”，但只要该 gameId 仍有任一上架版本就必须拒绝整游戏删除。删除最后一个版本后同步删除 `game_ownership`，该 gameId 可由后续上传者重新取得。

### 3.7 多人联机头像

采用固定平台 Bucket 方案：

```text
/bucket/_sys-user-avatars/{userId}.png
```

选择此方案的原因：

1. 完全沿用现有 `/bucket/{bucket}/{file}` 路由结构。
2. 不新增 `/bucket/{file}` 特例。
3. 不改变游戏 SDK 的 `getBucket()` 和 `upload()` 定义。
4. 游戏收到的是普通同源相对 URL，展示成本最低。
5. 平台只需增加 `_sys-` 保留前缀和稳定文件名的内部读写逻辑。
6. 后续新增平台 Bucket 时统一命名为 `_sys-xxxx`，无需继续维护单个名称黑名单。

App 玩家头像同步成功后显示实际图片；未同步、无自定义头像或同步失败时显示默认头像。HTML 玩家没有头像上传能力。

### 3.8 开发者 AI 提示词

现有提示词管理界面继续支持查看、编辑本地自定义内容和恢复默认，但默认内容的来源统一为：

```text
assets/playmesh-library/public/developer/prompts
```

界面规则：

1. 模板列表的 ID、名称、分类和文件名从该目录内的 `manifest.json` 加载，不再在 Dart 中维护另一份清单。
2. 未自定义时，编辑器显示当前安装包内对应 `.txt` 文件的原始内容。
3. 已自定义时显示“已自定义”状态，实际调用优先使用本地覆盖文件。
4. “恢复默认”只删除本地覆盖，然后重新读取安装包内的默认模板；界面不得保存或拼接一份内置回退文案。
5. 默认模板缺失、清单非法或正文为空时显示明确诊断并禁止发起依赖该模板的 AI 请求。
6. 调整默认提示词只需修改该目录中的模板文件并重新打包，不要求同步修改 Dart 或 JavaScript。
7. 用户本地覆盖不写回仓库、不进入游戏 ZIP，也不进入 Playmesh 发行包。

### 3.9 App 与开发者工作区 UI 重设计

设计基线：

- 使用 `frontend-design` 技能确定视觉方向、信息层级、字体、色彩和响应式布局。
- 使用 `web-design-guidelines` 技能审查开发者工作区和 go-server Web；实现时以当日最新规则重新审查，不把本文件中的规则副本当作永久最新版。
- 产品对象是局域网优先的 HTML 游戏平台，主要用户是玩家和游戏开发者；主界面的首要任务是找到并运行已有游戏。
- 视觉方向为“安静、内容优先的游戏控制台”，取消营销式首屏、装饰光球、大面积渐变和卡片堆叠。

基础视觉令牌：

| 角色 | 日间 | 夜间 | 用途 |
| --- | --- | --- | --- |
| Canvas | `#F4F7F6` | `#101614` | 页面背景 |
| Surface | `#FFFFFF` | `#18201D` | 工具栏、列表和面板 |
| Ink | `#17211D` | `#EAF1ED` | 主文本 |
| Emerald | `#087F6D` | `#4CC7AE` | 主操作与运行状态 |
| Electric Blue | `#2F6FED` | `#78A6FF` | 链接、在线源和焦点 |
| Danger | `#C24141` | `#FF8D86` | 破坏性操作和错误 |

字体：

- UI 正文与标题：`Noto Sans SC`，后备为 `Segoe UI Variable`、系统无衬线字体。
- gameId、版本、日志和代码：`JetBrains Mono`，后备为 `Cascadia Code`、`Consolas`。
- 不按视口宽度缩放字号，不使用负字距；标题通过层级、字重和留白建立识别。

识别性元素：

- 游戏列表使用“游戏图标 + 内容 + 窄状态轨道”，状态轨道统一表达本地、在线、可升级和运行中，不增加装饰图形。
- 面板、列表项和工具表面圆角不超过 8 px；页面区段不包装成浮动卡片，单个游戏项和对话框才可使用边框容器。

App 首页固定展示顺序：

```text
Playmesh / 资料与设置

本地游戏库                         第一展示项
  已安装游戏摘要 / 进入完整游戏库

在线游戏库                         第二展示项
  浏览游戏源 / 进入在线游戏库

其他入口                           最后展示
  加入对局 / 开发者工作区 / 用户资料 / 设置
```

规则：

1. 删除现有营销式 Hero；品牌、头像和设置保留在紧凑顶栏。
2. 本地游戏库使用现有 `featuredGame` 和游戏库路由，不新增首页扫描、启动或数据请求逻辑。
3. 在线游戏库位于本地游戏库之后，继续调用现有在线游戏库路由，不在首页预取在线数据。
4. 其他入口使用紧凑命令列表或图标工具栏，不与两个游戏库争夺首屏视觉权重。
5. 桌面宽度下两个游戏库使用连续全宽区段；移动端按相同顺序纵向排列，首屏必须看到本地游戏库和在线游戏库入口。
6. 空游戏库仍把本地游戏库放在第一位，并直接提供现有导入操作；不以营销文案代替空状态。

开发者工作区 HTML：

```text
项目选择 / 当前文件状态          保存  运行  发布  AI  更多
----------------------------------------------------------
项目树                  编辑器                   运行/日志
----------------------------------------------------------
状态、版本与连接状态
```

规则：

1. 保留“项目树、编辑器、运行/日志”三栏工作模型和移动端“项目、编辑、运行”三视图。
2. “运行”和“发布”并列为主要命令；保存使用熟悉的保存图标，AI 与低频操作降为次级。
3. 使用 Lucide 图标替换 `▶`、`✨`、`⋯`、`⌫` 等手工符号；图标按钮必须有 tooltip 与可访问名称。
4. 桌面端保持紧凑工具密度，编辑器占据最大空间；运行状态、二维码、链接和日志保持在右栏，不改运行逻辑。
5. 移动端顶栏只保留项目、保存、运行、发布和更多；其余命令进入菜单，不能产生横向滚动。
6. 合并 `workspace.css` 与 `workspace-v1.css` 的冲突规则，形成一套令牌化样式；不使用 `transition: all`。
7. 视觉改造期间保留所有现有元素 ID、请求路径、事件名称和 `workspace.js` 操作语义。

### 3.10 可配置国际化与主题

覆盖界面：

- Flutter App 全部页面与对话框。
- Developer Gateway 开发者工作区 HTML。
- go-server 公共页面、登录/注册、用户门户和管理员后台。

不翻译：

- API JSON 的 `code`、`message`、字段名和状态值。
- gameId、版本、Token、URL、文件路径和 SDK 标识符。
- 游戏包、游戏源和用户输入的名称、介绍、发布者及其他内容。
- 日志、代码、Manifest 原文和服务端诊断原文。

语言能力必须由配置清单驱动：

```json
{
  "manifestVersion": "1.0.0",
  "defaultLocale": "zh-CN",
  "locales": [
    {
      "id": "zh-CN",
      "label": "简体中文",
      "enabled": true,
      "fallback": null,
      "bundles": {
        "app": "locales/zh-CN/app.json",
        "developer": "locales/zh-CN/developer.json",
        "goServer": "locales/zh-CN/go-server.json"
      }
    }
  ]
}
```

以上 JSON 仅说明配置结构，不构成代码内置语言列表；实际可用语言完全以发行时清单为准。

配置规则：

1. 语言选择器只枚举 `enabled=true` 的条目；不得在 Flutter、JavaScript、Go 或 HTML 中写死语言列表。
2. `defaultLocale`、显示名称、回退关系和各端词典路径均来自清单。
3. 新增语言只新增词典并修改清单，不修改业务代码；构建校验所有启用语言的必填 key、回退环和文件完整性。
4. App 和发行构建使用仓库统一清单；go-server 可在 `server.json` 中覆盖默认语言、启用语言集合和是否显示语言切换，但覆盖值必须引用清单中的 locale ID。
5. 首次使用按“用户保存值 -> 系统/浏览器语言 -> 配置默认语言”选择；系统语言没有精确匹配时先匹配语言主标签，再使用回退链。
6. UI 根据 API 稳定 `code` 映射本地化提示；找不到映射时显示 API 原始 `message`，服务端不根据 `Accept-Language` 改写 JSON。

主题能力：

1. 所有界面使用语义令牌，不允许页面组件直接散落日间/夜间颜色。
2. 模式提供“跟随系统、日间、夜间”三项，并由配置决定是否允许用户切换及默认模式。
3. Flutter 使用 `ThemeMode.system/light/dark`；Web 在首帧前设置 `html[data-theme]` 和 `color-scheme`，避免加载闪烁。
4. Developer Workspace 的 CodeMirror、Diff、日志和二维码容器与主题同步；二维码始终保留可扫描的高对比白底静区。
5. App 偏好保存在本机 UI 配置；Developer Workspace 与 go-server Web 使用当前浏览器本地偏好，互不写入游戏数据、API Token 或用户上传包。
6. 系统主题运行时变化应立即生效；用户显式选择日间或夜间后不再跟随系统，直到切回“跟随系统”。
7. 国际化与主题在相关交互契约、路由和表现层边界冻结后即可进入对应批次，可与其他独立批次交错，但必须在正式发布前完成全平台回归。

5. Go Core、go-server、Developer CLI 分别在各自 module 执行格式化、定向测试和 `go test ./...`；涉及并发状态时增加 race/并发压力验证。

7. 平台正式构建单独请求授权，并按 HarmonyOS、Android、Windows 顺序在沙箱外串行执行；不并行启动两个 Flutter 构建。
8. 命令被拒绝或环境缺失时明确记录“未执行”，不得写成“通过”；构建成功也不得替代安装、真机、生产签名和真实网络验证。
9. 测试失败先保留首个具体异常，修复后重跑失败用例、所属测试组和最终全量回归。
10. 最终验证记录写入 `docs/verification/`，并同步 `docs/version/NEXT.md`；记录命令、环境、结果、产物摘要、未验证项和残余风险。

### 3.12 四类设备与键盘/遥控器操作

覆盖范围：

- App 首页、游戏库、在线游戏库、详情、配置、登录、设置、资料、加入对局和开发者入口。
- 全部 Dialog、BottomSheet、Menu、Tooltip、Snackbar action、搜索、表单和列表。
- 本地/远程游戏页面覆盖层、返回/关闭按钮、分享页和性能面板。
- `GameToolDock` 收起悬浮球、展开工具条、“更多”菜单及所有二级操作。
- WebView 内由 Playmesh SDK 注入的昵称、能力确认、信息、日志、关闭、展开菜单和悬浮工具。
- Developer Workspace WebView 的项目菜单、编辑器、运行、发布、AI、模态框和移动导航。

统一输入映射：

| 意图 | 键盘 | Android TV 遥控器 |
| --- | --- | --- |
| 移动焦点 | Tab/Shift+Tab、方向键 | 上/下/左/右 |
| 激活 | Enter、Space | DPAD_CENTER/Select |
| 返回/关闭当前层 | Escape、Browser Back | Back |
| 打开平台游戏工具 | F10 或 Menu | Menu；无 Menu 键时长按 DPAD_CENTER |
| 翻页/滚动 | PageUp/PageDown、方向键 | 方向键，边缘时继续滚动 |

焦点规则：

1. 每个页面首次进入时聚焦首个主要操作或页面标题后的第一个控件，不自动聚焦文本框。
2. 焦点顺序与视觉阅读顺序一致；隐藏、禁用或离屏控件不能获得焦点。
3. 打开菜单后聚焦第一个可用项；关闭后把焦点还给触发按钮。
4. Dialog、Sheet 和覆盖层打开时焦点限制在当前层；关闭后恢复到原触发点。
5. 焦点样式在日间和夜间都清晰，不能只依赖颜色；至少包含 2 px 高对比轮廓或等价视觉变化。
6. 列表焦点移动到视口外时自动滚动到完整可见；异步刷新后按稳定 gameId/sourceId 恢复焦点，不按旧下标恢复。
7. Android Back 先关闭最上层菜单/弹窗/工具，再执行页面返回；破坏性离开仍保留确认。
8. WebView 获得输入焦点时，平台快捷键仍可把焦点转移到 Playmesh 工具；返回游戏内容时恢复此前网页焦点。
9. 拖动悬浮球不是必需操作。增加“移动工具位置”键盘模式：方向键移动，Enter 保存，Escape 取消；触摸和鼠标仍可直接拖动。

设备布局矩阵：

| 设备 | 基线 | 布局要求 |
| --- | --- | --- |
| TV | 1280 x 720、1920 x 1080，横屏，3 米观看 | 10-foot 字号与间距、明显焦点、无触摸依赖、安全区、列表分段加载 |
| 平板 | 600-1366 dp，横竖屏，触摸/键盘 | 双栏或主从布局按空间切换，保持触控目标和键盘顺序 |
| 手机 | 320-600 dp，横竖屏，触摸/软键盘 | 单栏、SafeArea、无横向滚动，软键盘不遮挡当前字段与提交操作 |
| 电脑 | 800 x 600 至宽屏，可调整窗口，鼠标/键盘 | 紧凑高密度、可见 hover/focus、窗口缩放不重叠 |

Android TV 包要求：

1. Android Manifest 声明触摸屏非必需，并按发行目标提供 Leanback/TV 启动能力与 TV banner。
2. 不把 portrait 作为 App 导航页面的强制方向；游戏运行页仍按 Manifest 角色方向规则处理。
3. 遥控器按键通过 Flutter Shortcuts/Actions 和 WebView 平台桥统一映射，不在每页分散处理原始 keyCode。
4. 文本输入只在用户确认搜索框/表单后打开 TV 软键盘，退出输入后焦点返回该控件。

### 3.13 游戏内一键打开分享与默认覆盖层状态

Authority 客户端中的游戏可以直接调用：

```js
await playmesh.app.ui.openSharePanel();
```

调用后打开 App 当前游戏页已有的“二维码与链接”分享界面，等价于用户在展开的游戏工具中选择“二维码与链接”。游戏不需要先展开悬浮球；该 UI 方法本身不返回二维码、
Token 或分享链接。App-only 本机房主需要读取数据时使用独立的
`playmesh.app.lan.getShareLinks()`，两者仍读取同一分享状态。

界面行为：

1. 仅 `playmesh.main.session.isAuthority() === true` 的当前前台游戏可以调用。
2. 分享界面已经打开时重复调用只把焦点移回当前分享界面，不创建第二层、不重复启动服务。
3. Promise 在分享界面成功显示后完成，不等待用户关闭。
4. 用户关闭后焦点回到调用前的游戏 WebView 控件；Android TV 返回键先关闭分享层，不退出游戏。
5. App 后台、游戏页面已销毁、非 Authority 或分享能力不可用时返回稳定错误。
6. 现有悬浮工具中的“二维码与链接”按钮继续保留，两种入口共用 `_openShare()` 和同一状态。

每次新建、进入、重新载入或切换游戏运行页时，平台覆盖层初始状态固定为：

```text
GameToolDock.expanded = false
GameToolDock.moreMenuVisible = false
performanceOverlayVisible = false
shareOverlayVisible = false
infoOverlayVisible = false
logsOverlayVisible = false
debugOverlayVisible = false
```

默认只显示收起的悬浮球；不恢复上一局或上一个页面的 FPS、菜单或覆盖层打开状态。

### 3.14 非顺序实施与合并批次

FR-01 至 FR-26 是验收索引，不是线性待办。实际开发先建立依赖图：

```text
开发文档与版本基线
  -> 数据/协议/注册表事实源
     -> 各业务模块
        -> 生成物与 UI
           -> 跨模块契约
              -> 全量验证与发行包
```

建议按共享改动聚合：

| 合并批次 | 一次处理的相关内容 |
| --- | --- |
| Catalog 与本地库 | 源配置、publicURL、首页、搜索、latest offer、图标、热度、更新检查 |
| go-server 新 schema | 用户、注册开关、验证、密钥、所有权、版本、上下架、删除、上传与 locale 配置 |
| SDK 注册表 | avatar、Authority 分享入口、注入 UI 键盘支持、声明、版本、模板、提示词和生成物 |
| 游戏运行容器 | 分享界面、覆盖层默认状态、悬浮工具、焦点、TV 按键、头像同步和四端布局 |
| Web 表现层 | Developer Workspace/go-server 的重设计、国际化、主题、键盘、可访问性 |
| 发行与回溯 | 文档、版本日志、完整沙箱外测试、生成物复核和平台构建 |

执行者可以拆分、合并或交错这些批次，但必须遵守：

1. 先完成被依赖的 schema、契约或注册表，再实现消费端。
2. 同一数据库使用一个新 schema 设计完成，不为每个 FR 连续迁移。
3. 同一 SDK 版本在相关方法稳定后统一生成，不在每个小改动后反复提交生成物。
4. 同一页面集中完成数据、视觉、国际化、主题和焦点改造，避免多轮重写布局。
5. 每个批次仍执行定向测试；减少重复不等于推迟所有测试到最后。
6. 跨批次接口稳定后尽早执行契约测试，最终仍执行 FR-23 全量验证。
7. 新发现的依赖或用户追加要求先更新依赖图，再调整批次，不机械回到 FR 编号顺序。

## 4. 二十六项详细开发规格

### FR-01 分享游戏时显示本地源名称

游戏分享页“二维码与链接 -> 服务器”中的以下位置统一使用 `OnlineGameSource.name`：

- 服务器候选列表
- 连接中状态
- 已连接标题
- 连接失败后的源名称

`GameCatalogDeclaration.name` 只在游戏源详情页以“源官方名称”展示。

### FR-02 导出命名、清理和内存控制

导出和系统分享统一使用：

```text
游戏名称-v游戏版本.zip
```

示例：

```text
星海竞速-v2.0.0.zip
```

要求：

1. 清理 Windows 和 Unix 禁止文件名字符及结尾点空格。
2. 名称为空时回退为 `game`。
3. 每次分享开始前清理专用临时目录中的旧分享文件。
4. 删除前校验解析后的绝对路径仍位于专用目录内。
5. 能可靠获知分享完成的平台，在 `finally` 删除当前文件。
6. 不能可靠获知消费完成的平台，在下次分享或 App 启动时删除。
7. ZIP 改为流式写文件，避免同时在内存中保存源文件集合和完整压缩结果。
8. 并发任务使用唯一临时路径，不共享固定文件。

验收标准：

- 连续分享 20 次后最多保留 1 个当前分享文件。
- 取消、失败和 App 重启后能够清理旧文件。
- 64 MiB 包导出时常驻内存不随分享次数增长。

### FR-03 首页与非破坏性聚合搜索

`OnlineGameLibraryPage` 拆为首页和搜索两个控制器状态。

首页模型：

```text
HomeCatalogResult
  sections: SourceSectionResult[]

SourceSectionResult
  source
  offers
  total
  nextCursor
  error
```

搜索模型：

```text
AggregatedGameResult
  gameId
  publisher
  publisherKey
  groupKey = gameId + publisherKey
  heat = localUsage[gameId].launchCount ?? 0
  lastOpenedAt = localUsage[gameId].lastOpenedAt
  representative
  versions: AggregatedVersion[]

AggregatedVersion
  version
  offers: CatalogGameOffer[]
```

聚合控制器必须先按 `gameId + publisherKey` 分组，再在每组内部整理版本。不得先按 `gameId` 合并后再选择一个发布者，否则会丢失同 ID 的其他发布者摘要。

聚合控制器按 gameId 读取本机 `GameLibraryUsageStats` 得到 `heat` 和 `lastOpenedAt`，再对完整聚合结果执行热度倒序排序。源返回顺序不能直接作为 App 搜索最终顺序。

每个源维护独立分页或 cursor，不再向所有源发送一个全局页码。

### FR-04 游戏包根 icon.png

包结构：

```text
game.zip
  main.json
  icon.png       // 可选
  capabilities.json
  app/
```

约束：

- 文件名必须精确为 `icon.png`。
- 只允许 PNG。
- 最大 2 MiB。
- 建议边长 64 到 1024 像素。
- 解码失败、超限或图片炸弹风险时忽略并显示默认图标。

本地游戏库：

- `GameSummary` 增加可选本地图标引用。
- 列表使用固定 56 x 56 容器。
- 图片失败时显示默认图标。
- 图片加载不得改变卡片尺寸。

在线游戏库：

```json
{
  "icon": "https://games.example.com/apps/icon?id=com.example.game&version=2.0.0"
}
```

规则：

- 图标 URL 必须与源 Host 同源。
- App 使用该源读取 Token 请求图标。
- 跨源 URL、404、坏图片或超限图片均回退默认图标。

删除 `main.json.icon` 的旧列表图标语义；实现只读取包根目录可选 `icon.png`，旧字段存在时忽略。

### FR-05 游戏源详情

详情页缓存优先渲染，再后台刷新 `/apps/info`。

游戏 `author` 显示为“发布者”；源声明 `author` 显示为“建造者”。

### FR-06 go-server 用户登录注册

注册字段：

- 邮箱
- 密码
- 确认密码
- 图形验证码答案

账号规则：

- 邮箱规范化后大小写不敏感唯一。
- 密码建议 10 到 128 字符。
- 密码使用高成本自适应哈希保存。
- 登录成功创建 Secure、HttpOnly、SameSite=Lax 用户会话 Cookie。

管理员配置：

```text
allow_user_registration: true | false
require_email_verification: true | false
```

两个开关相互独立：`allow_user_registration` 只控制是否创建新账号；`require_email_verification` 只控制允许注册时新账号是否必须验证邮箱。

关闭验证：

```text
注册成功 -> 账号 active -> 可立即登录
```

开启验证：

```text
注册成功 -> 账号 pending_verification
         -> 禁止登录
         -> 点击邮件一次性链接
         -> 账号 active
```

重发验证邮件：

- 最短间隔 60 秒。
- 每账号每小时最多 5 次。
- 返回统一结果，避免邮箱枚举。
- 新 Token 生成后旧未使用 Token 失效。

展示名称：

- 注册成功后默认等于注册账号，即用户提交并规范化保存的邮箱账号。
- 用户可在账号设置中修改展示名称。
- 建议 1 到 40 个字符。
- 上传时服务端使用当前展示名称覆盖包内 `author`。

上传密钥：

- 用户可自动生成或手工输入。
- 长度 10 到 128。
- 至少包含 1 个小写字母、1 个大写字母、1 个数字和 1 个特殊字符。
- 不允许空白和控制字符。
- 服务端只存 HMAC-SHA256，HMAC 使用独立 Pepper。
- 明文只在创建或轮换成功时展示一次。
- 轮换后旧密钥立即失效。

### FR-07 作者展示改为发布者

以下所有游戏作者标签统一改为“发布者”：

- 本地游戏库
- 在线游戏库
- 游戏详情
- 下载任务
- 开发者工作区
- go-server 公共页面
- 用户门户
- 管理员审核页

只改展示文案，不修改 `main.json.author`、数据库 `author` 和 Catalog `author` 字段名。

### FR-08 App 多源发布

App 每个源可单独保存上传密钥。

发布候选源过滤条件：

```text
source.enabled == true
&& source.declaration.userUpload.supported == true
&& source.uploadKey.trim().isNotEmpty
```

只有同时满足三项条件的源才进入发布弹窗。任一条件不满足的源直接从候选列表排除，不显示禁用项。若没有可发布源，弹窗显示空状态并提供“前往游戏源配置”操作。

发布接口使用：

```http
Authorization: UploadKey <upload-key>
```

限流：

- 同 IP 每 30 秒最多 1 次上传请求。
- 建议同时增加同上传密钥每 30 秒最多 1 次。
- 限流在读取大请求体之前执行。
- 触发时返回 `429` 和 `Retry-After`。

上传成功后：

1. 安全扫描 ZIP。
2. 解析 Manifest。
3. 判断 gameId 所有权。
4. 用账号展示名称覆盖 `author`。
5. 创建 pending 审核记录。
6. 将记录绑定到当前用户。

### FR-09 gameId 所有权冲突

数据库使用稳定映射：

```text
game_ownership.package_id -> users.id
```

上传事务：

1. `game_ownership` 不存在时，为当前用户原子创建。
2. owner 等于当前用户时允许上传新版本。
3. owner 不等于当前用户时返回 `409 game_ownership_conflict`。
4. 冲突时不得保存 ZIP、图标或审核记录。
5. 删除任意版本后检查该 gameId 是否仍有版本；存在其他版本时保留所有权，最后一个版本删除后同步释放所有权。
6. 新数据库从第一条用户上传开始建立所有权；旧匿名数据库不进入本版本运行范围。

### FR-10 publicURL 单输入框导入

二维码、复制链接、手工输入和扫码结果统一为：

```text
https://games.example.com?token=published-read-token
```

App 添加源页面只显示一个输入框：

```text
游戏源链接
```

统一导入算法：

1. 去除首尾空白并解析 URI。
2. 只接受 HTTP/HTTPS。
3. 要求有效 Host。
4. 拒绝 userInfo 和 fragment。
5. 只接受可选 `token` 查询参数。
6. 保存时把 Host 和 Token 分离。
7. 请求 `host/apps/info`。
8. Token 非空时使用 `Authorization: Bearer`，不继续把 Token 放在探测 URL 中。
9. 要求 HTTP 200、JSON 合法、Catalog API 精确为 2.0.0、能力声明内部一致。
10. 成功后才保存；本地名称初始化为官方名称，缺失时使用 `host:port`。
11. 网络、超时、TLS、鉴权、版本或声明错误都视为导入失败。
12. 导入失败不得新增配置，也不得覆盖同 Host 的已有配置。

扫码和手工输入共同调用：

```text
verifyAndUpsertSource(rawValue)
```

#### App 自身暴露的只读游戏源

App 自身可把本地游戏库暴露为局域网游戏源。App 生成的“复制游戏源链接”和二维码也必须使用完全相同的格式：

```text
http://192.168.1.20:16668?token=<app-read-token>
```

规则：

1. `publicURL` 使用当前 App 对其他设备可访问的 HTTP 地址，不使用 `playmesh://`。
2. 二维码内容与复制出的文本逐字一致，只包含 `publicURL?token=...`。
3. Token 只授予读取本机 Catalog 和下载游戏包的权限。
4. App 自身源只实现 `/apps/info`、`/apps/list`、`/apps/icon` 和 `/apps/download`。
5. App 自身源不提供用户注册、登录、上传密钥、游戏包上传、审核、上架或下架接口。
6. `/apps/info` 必须声明 `userUpload.supported=false`，不得返回上传 path、协议版本或上传大小。
7. 开发者工作区发布候选源过滤时，App 自身源因不支持上传而不会显示。
8. App 自身源的 token 不得被当作上传密钥使用；向不存在的上传接口请求时返回 404 或能力不支持错误。
9. 其他 App 导入该链接时仍先请求 `/apps/info`；探测成功后保存为普通只读在线源。
10. IP 或端口变化后重新生成链接和二维码，旧地址不保证继续可达。

App 自身源的能力声明示例：

```json
{
  "catalogApiVersion": "2.0.0",
  "name": "林舟的本地游戏库",
  "author": "Playmesh App",
  "homepage": null,

    "supported": false
  }

```

### FR-11 自定义用户头像与权威主机映射

本地资料模型升级为 v2，保存：

- `userId`
- `nickname`
- 头像相对路径
- 头像 SHA-256
- 头像更新时间

不读取旧 `avatarLabel` 资料格式；旧资料文件隔离后创建新 profile，未设置图片时显示默认头像。

多人会话流程：

1. 权威 App 创建会话后清理本会话遗留头像。
2. 权威 App 保存自己的头像。
3. 远端 App 玩家加入或重连后发送头像摘要。
4. 权威主机已有相同摘要时不重复传输。
5. 摘要不同或文件不存在时请求 PNG 内容。
6. go-core 使用会话 Bearer 凭据识别发送者。
7. 只允许 `source=lan_app` 上传本人头像。
8. 权威主机再次校验 PNG、大小、尺寸和玩家身份。
9. 使用临时文件加原子替换保存为：

```text
/bucket/_sys-user-avatars/{authenticatedPlayerId}.png
```

10. 保存成功后设置 `Player.avatar` 并广播 `session.state`。
11. 保存失败时 `avatar` 保持 `null`，不得阻止玩家入局。
12. 玩家暂时断线时保留头像；会话结束时清理保留 Bucket。

保留 Bucket 实现规则：

- 平台保留 Bucket 统一使用 `_sys-xxxx` 命名，头像 Bucket 固定为 `_sys-user-avatars`。
- 游戏传入的 Bucket 只要以 `_sys-` 开头，就在进入存储层前统一返回“平台保留 Bucket”错误。
- 不再维护 `_sys-user-avatars` 等单个名称黑名单；未来新增 `_sys-cache`、`_sys-session-*` 时自动受同一规则保护。
- 不放宽普通 Bucket 的时间戳文件名规则。
- 普通游戏 Bucket 继续使用现有校验规则；平台内部增加独立的系统 Bucket 校验器和 `avatarFile(playerId)` 原子写入方法。
- 系统 Bucket 校验建议使用 `^_sys-[A-Za-z0-9][A-Za-z0-9_-]{0,58}$`，总长度不超过 64 个字符。
- HTTP 仍使用现有 `/bucket/{bucket}/{file}` 三段式路由。
- 普通 Bucket 继续使用原缓存规则。
- `_sys-user-avatars` 使用 `ETag + Cache-Control: no-cache`，避免固定 URL 更新后仍读取旧头像。

### FR-13 本地游戏使用统计与热度排序

热度不再依赖 go-server 下载计数。App 使用本机游戏启动次数作为当前用户自己的热度值，并把最近打开时间与启动次数放在同一条可扩展统计记录中。

目标结构：

```json
{
  "version": 2,
  "games": {
    "com.example.game": {
      "lastOpenedAt": 1785060000000,
      "launchCount": 42
    }
  }
}
```

统计对象：

```text
GameLibraryUsageStats
  lastOpenedAt: DateTime?
  launchCount: int
  extensions: Map<String, JSON>
```

记录规则：

1. 游戏每次进入实际 `GamePage` 路由时执行一次 `markLaunched(gameId, openedAt)`。
2. 同一原子写入同时设置 `lastOpenedAt=openedAt` 和 `launchCount=launchCount+1`。
3. WebView 刷新、联机重连、前后台切换和同一次运行内页面重建不得重复增加。
4. 启动次数使用 JSON 安全整数，上限为 `9007199254740991`；达到上限后保持饱和，不溢出或归零。
5. 游戏删除时同步删除该 gameId 的整条统计对象。
6. 本地统计只存在 `playmesh-library/cache/app/game-library.json`，不进入游戏包、导入导出、项目历史、Catalog 或 go-server。

格式规则：

1. 只读取 `version=2` 和 `games` 对象，不识别 v1 `lastOpenedAt` 映射。
2. 检测到旧版本或未知版本时，把原文件改名为带时间戳的 `.unsupported` 备份，并创建空 v2 文件。
3. 损坏 ID、负数时间、非法对象或非法计数忽略，不能阻止游戏库启动。
4. 每个游戏对象中的未知合法 JSON 字段原样保留，方便后续增加累计时长、成就统计等数据而不再次重构顶层结构。

容量与清理：

1. 保持现有 `maxEntries=2048` 硬上限。
2. 每次读取完成和写入前执行清理；超过上限时按 `lastOpenedAt` 最旧优先淘汰。
3. 没有有效 `lastOpenedAt` 的记录先于有时间记录淘汰；同时间再按较小 `launchCount`、gameId 正序决定。
4. 游戏库扫描确认某 gameId 已不存在时清理对应记录；显式删除游戏时立即清理。
5. 单条统计对象序列化后最大 16 KiB；未知扩展字段导致超限时丢弃扩展字段，但保留 `lastOpenedAt` 和 `launchCount`。
6. 整个元数据文件最大 4 MiB；超过时先执行无效项和过期项清理，再按淘汰顺序缩减到限制内。
7. 写入继续使用同目录临时文件、flush 和原子替换；写入失败不得破坏上一份有效文件。
8. 内存缓存改为 `Map<String, GameLibraryUsageStats>`，对外返回不可变快照，写操作继续串行化。

搜索热度：

```text
heat(group) = localUsage[group.gameId]?.launchCount ?? 0
```

App 内本地游戏库搜索和在线游戏库搜索都使用该热度。在线一级摘要显示“热度 N”；本地游戏详情页在现有状态信息区域内并列显示“最近打开”和“启动次数”，不增加独立卡片。

搜索结果按以下顺序排列：

1. `launchCount` 倒序。
2. `lastOpenedAt` 倒序。
3. 组内最高语义版本倒序。
4. 游戏名称正序。
5. `groupKey` 正序。

因为本地统计只按 gameId 保存，同 gameId 的不同发布者摘要共享相同启动次数和最近打开时间。该热度代表当前设备用户的使用偏好，不是全局下载量或跨用户排行榜。

go-server 公共网页无法读取 App 本机统计，因此不使用这套个性化热度；其公共列表保持服务端稳定排序。Catalog 也不新增 launchCount 字段。

### FR-14 是否允许用户注册

go-server 运行配置新增：

```json
{
  "allowUserRegistration": true,
  "requireEmailVerification": false
}
```

行为规则：

1. `allowUserRegistration=true` 时，公共导航显示“登录 / 注册”，注册接口按正常流程创建账号。
2. `allowUserRegistration=false` 时，公共导航同时隐藏“登录”和“注册”入口，不在首页提示账号功能。
3. `/login` 路径始终可直接访问，已有 active 用户正常登录。
4. `/register` 路径始终可直接访问，但关闭注册时表单禁用并显示“当前游戏源未开放用户注册”。
5. 即使客户端绕过页面直接提交，`POST /api/user/auth/register` 也必须在验证码和密码处理前读取服务端开关并拒绝。
6. 注册关闭时接口返回 `403 registration_disabled`，不得创建用户、验证 Token、会话或发送邮件。
7. 已注册用户的登录、退出、邮箱验证、重发验证邮件、账号设置、上传密钥和游戏管理均不受影响。
8. 已创建但尚未验证邮箱的账号仍可完成验证；验证成功后可正常登录。
9. 管理员修改开关后立即生效，不要求重启服务，并记录配置审计事件。
10. UI 隐藏只是展示策略，服务端注册接口必须始终独立执行开关校验。

默认建议 `allowUserRegistration=true`，由管理员按运营阶段关闭。关闭后不应返回 404，以便用户通过固定登录地址继续使用已有账号。

### FR-15 管理员上下架与作者删除已下架游戏

权限定义：

1. “游戏作者”操作权限实际根据 `games.owner_user_id` 判断，不根据可修改的 `author` 展示字符串判断。
2. 管理员可对任意 `approved` 版本执行上架或下架。
3. 游戏所有者可对自己的 `approved` 版本执行上架或下架。
4. pending 和 rejected 版本不能直接上架。

所有者删除规则：

1. `approved + published` 不允许直接删除，返回 `409 game_must_be_unpublished`。
2. `approved + unpublished` 允许所有者物理删除版本记录、ZIP、图标和该版本派生文件。
3. pending 和 rejected 仍允许所有者删除。
4. 删除单个版本不影响同 gameId 的其他版本。
5. “删除全部已下架版本”必须在事务内再次确认该 gameId 没有任何 published 版本。
6. 删除后若仍有其他版本，保留 `game_ownership`；删除最后一个版本时在同一事务中删除 `game_ownership`，其他账号之后可重新声明该 gameId。
7. 删除后 Catalog 缓存和公开列表立即失效，不得继续下载已删除路径。
8. 数据库记录与文件删除使用可恢复顺序：先在事务中标记 deleting，再删除文件，最后删除版本记录；失败时后台任务继续清理。
9. 审计日志保留操作者账号、管理员/所有者角色、gameId、版本、原状态、目标状态和时间，但不保留已删除包内容。

管理员后台：

- approved + published 显示“下架”。
- approved + unpublished 显示“上架”。
- pending 只显示审核通过/拒绝。
- rejected 不显示上架操作。
- 管理员上架/下架与用户操作使用同一状态服务和事务，不复制两套规则。

### FR-16 每个源只公开最新版本

最新版本定义：

1. 对同一 gameId 的所有 `approved` 版本使用统一三段式语义版本比较。
2. MAJOR、MINOR、PATCH 数值最大的记录为当前最新 approved 版本。
3. 相同版本若因并发异常出现多条记录，启动完整性检查并拒绝 Catalog 服务，不随机选择。

公开规则：

1. `/apps/list` 每个 gameId 最多返回一条 offer。
2. 只有当前最新 approved 版本为 `published=true` 时才返回该游戏。
3. 最新版本已下架时，整个 gameId 不公开，不自动回退到较旧的已审核版本。
4. 新版本审核通过时，在同一事务中将所有旧版本设为 `published=false`，并按审核结果决定新版本是否上架。
5. 管理员和所有者只能上架当前最新 approved 版本；上架旧版本返回 `409 not_latest_version`。
6. `/apps/download?id=...&version=...` 只允许 version 等于当前公开最新版本，旧版本返回 `404 version_not_available`。
7. `/apps/icon` 使用相同版本可见性规则，不能借图标接口探测旧版本。
8. App 自身只读游戏源也执行相同规则。
9. 历史版本继续在所有者和管理员后台显示，可下架和删除，但不存在公共下载入口。

跨源聚合：

- 每个源最多贡献一个 latest offer。
- 不同源的最新版本可以不同，因此聚合版本页仍可能显示多个版本。
- 点击某版本只显示“当前最新版本等于该版本”的源。
- App 若发现同一 sourceId 返回同 gameId 的多个版本，将该源对应游戏标记为协议错误并排除多余项。

### FR-17 打开游戏库时后台检查更新

检查输入：

```text
installedGames
enabledSources
sourceLatestOffers
```

匹配键：

```text
gameId + publisherKey
```

候选条件：

1. gameId 完全相同。
2. 发布者去除首尾空白后完全相同，不做别名或大小写合并。
3. 源 offer 是该源当前唯一最新版本。
4. 源版本符合 `MAJOR.MINOR.PATCH`。
5. 源版本严格大于本地安装版本。

结果模型：

```text
GameUpdateCandidate
  gameId
  publisher
  installedVersion
  versions[]
    targetVersion
    sources[]
      sourceId
      localSourceName
      host
      offer
```

执行规则：

1. 每次进入游戏库触发一次后台检查，不阻塞首屏。
2. 只查询已启用源，源错误彼此隔离。
3. 同一页面生命周期内检查任务去重，离开后再次进入重新检查。
4. 候选按目标版本倒序；同版本源按本地配置顺序。
5. 快速升级必须由用户确认版本和源，不自动下载或静默覆盖。
6. 下载后再次验证 gameId、发布者和版本，防止检查后源内容被替换。
7. 更新使用原子安装并保留游戏数据、启动统计和用户动态文件。
8. 更新成功后立即重新扫描，并继续检查是否仍存在更高版本。

### FR-18 上传版本必须严格递增

适用入口：

- 开发者工作区多源发布。
- go-server 登录用户网页门户上传。
- 任何后续新增的用户上传客户端。

服务端规则：

1. 包内 `version` 必须符合统一的 `MAJOR.MINOR.PATCH`。
2. 首次上传某 gameId 时接受任意合法三段版本。
3. gameId 已存在版本时，新版本必须严格大于当前数据库最高版本。
4. 相同版本返回 `409 version_already_exists`。
5. 低于当前最高版本返回 `409 version_must_increase`。
6. 错误响应返回 `currentHighestVersion`，供工作区和网页提示开发者修改。
7. pending、approved、unpublished 和 rejected 记录都参与当前最高版本计算；已经物理删除的记录不参与。
8. 不自动修改 `main.json`，开发者必须提高版本并重新打包。
9. gameId 所有权冲突优先返回 `game_ownership_conflict`，不得借版本错误泄露其他账号版本详情。
10. 所有权校验、最高版本查询、比较和版本记录创建位于同一数据库事务并锁定 gameId。
11. 数据库增加 `UNIQUE(package_id, version)` 作为并发兜底。
12. 校验失败时不保存 ZIP、图标、临时包或审核记录。

开发者工作区：

- 本地校验先拒绝非法版本格式。
- 多源发布逐源显示当前最高版本和“请提高 main.json.version”。
- 某些源成功、某些源因版本过低失败时不回滚成功源。

go-server 用户门户：

- 登录用户可在“我的游戏包”页面上传 ZIP。
- 上传使用用户会话和 CSRF，不使用匿名邮箱。
- 相同或更低版本错误显示当前版本与目标版本，不进入审核队列。

### FR-19 AI 默认提示词单一来源与打包同步

唯一真源：

```text
F:\Project\flutter\playmesh\assets\playmesh-library\public\developer\prompts
```

模板清单新增为：

```json
{
  "manifestVersion": "1.0.0",
  "templates": [
    {
      "id": "common",
```

运行时规则：

1. `DeveloperAiPromptTemplateStore` 从 Flutter Asset Bundle 读取 `manifest.json`，再按清单加载默认正文。
2. `project_prompt_operation`、`prompt_templates_operation` 和其他 AI 入口只能通过该 Store 取默认模板。
3. 删除任何硬编码的模板正文、备用默认字符串和重复模板资源；加载失败必须显式报错，不能回退到旧内容。
4. 本地 `developer/ai-prompts/{id}.txt` 仅作为用户自定义覆盖存在，不改变“默认提示词”的定义。
5. “恢复默认”删除覆盖文件后重新读取 Asset Bundle；当前进程内的模板缓存必须按资源版本失效。
6. 提示词正文不写入生成版本摘要；生成项目提示词时动态附加当前完整 `playmesh-main.d.ts` 与 `playmesh-app.d.ts`。

发行打包规则：

1. `pubspec.yaml` 及各平台构建配置必须包含整个提示词目录和 `manifest.json`。
2. Windows、Android、Harmony 以及后续新增的所有正式发行入口，统一先执行 SDK/契约生成，再执行提示词预检，最后启动平台构建。
3. 预检读取清单并计算每个模板源文件的 SHA-256；缺失、空文件、非法 UTF-8、重复 ID、孤立 `.txt` 或路径越界都立即终止构建。
4. 平台构建完成后，从实际安装包或发行目录读取对应 Asset 文件并再次计算 SHA-256，与构建前源文件摘要逐项比较。
5. 缺少 Asset、文件数量不一致或任一摘要不一致时删除本次未发布产物并使构建失败，不允许只打印警告。
6. 校验必须针对当前工作区文件重新计算，不接受上次构建缓存的摘要；因此修改任一模板后，下一次打包必然携带新内容。
7. 构建日志只记录相对路径、字节数和摘要，不输出提示词全文。
8. 普通开发运行与正式包使用同一 Asset 路径，不建立仅开发环境可见的默认模板目录。

发布物验收：

- Windows 发行目录中的 Flutter Asset 与源文件逐字节一致。
- APK/HAP 解包后的提示词 Asset 与源文件逐字节一致。
- 修改任一 `.txt` 后不改 Dart 代码即可构建成功，安装后的“默认内容”和“恢复默认”均显示新文本。
- 构建前后源文件若被并发修改，摘要复核失败并要求重新打包，不能产出内容不确定的安装包。

### FR-22 可配置国际化、主题与日夜间切换

统一语言资源根：

```text
assets/playmesh-localization/
  manifest.json
  locales/{localeId}/app.json
  locales/{localeId}/developer.json
  locales/{localeId}/go-server.json
```

发行时将 go-server 所需词典生成或复制到其可嵌入资源目录；源清单只有一份。生成产物不得成为手工维护的第二真源。

语言清单校验：

1. `manifestVersion`、locale ID、默认语言、回退语言和 bundle 路径合法。
2. locale ID 唯一，默认语言必须启用，fallback 必须存在且不能形成环。
3. 每个启用语言必须具有当前 UI 使用的全部消息 key；允许通过显式 fallback 继承，不允许静默显示 key。
4. 未在清单登记的词典和清单引用不到的文件都使构建失败。
5. 词典是合法 UTF-8 JSON，值只能是字符串或受控复数/参数对象，禁止可执行 HTML。
6. 代码扫描阻止新增 `locale == "..."`、固定 supportedLocales 数组和按语言分支拼接 UI 文案。
7. 正式构建后校验 App Asset、Developer Workspace 和 go-server 嵌入词典与源清单逐项一致，缺失或陈旧词典不得发布。

App：

- 启动时先加载语言清单，再创建动态 `supportedLocales` 和 UI 消息代理。
- 设置页提供语言下拉菜单和“跟随系统、日间、夜间”分段控件。
- 语言、主题模式和可选主题 ID 保存在 App UI 偏好文件，切换后即时刷新界面。
- Flutter/Material 内置组件、日期、时间、数字和复数使用所选 Locale 的标准格式化能力。

Developer Workspace：

- 文案使用 message key 或 `data-i18n`，对话框、菜单、placeholder、tooltip、空状态和校验提示统一从词典读取。
- 首帧前读取本地偏好并设置 locale 与主题，避免中文或亮色界面短暂闪现。
- CodeMirror 和运行面板跟随主题；代码、文件内容和日志不翻译。

go-server Web：

- `server.json` 增加 `webUI.defaultLocale`、`webUI.enabledLocales`、`webUI.allowLocaleSwitch`、`webUI.defaultThemeMode` 和 `webUI.allowThemeSwitch`。
- 配置省略时读取统一清单默认值；配置引用未知 locale 或主题模式时拒绝启动，不静默回退。
- 公共页、账号页、用户门户和管理员后台共用同一 locale/theme loader。
- 匿名与登录用户均可在 UI 切换；偏好保存于浏览器 cookie/localStorage，不要求修改用户账号和游戏数据库。

API 不国际化：

1. JSON 响应不读取 `Accept-Language`，同一请求在不同 UI 语言下返回逐字段相同的结构与机器码。
2. 错误 `code` 是 UI 翻译主键，原始 `message` 只作为无映射时的回退文本。
3. Catalog、上传、认证、管理员和 Relay API 都不返回翻译字典或 locale 变体。
4. HTML 页面路由可以根据 UI 偏好渲染文案，但 `/api/**`、`/apps/**` 和 SDK 契约保持不变。

### FR-24 全 App 键盘/Android TV 操作与四端适配

#### Flutter 输入架构

新增统一平台输入层：

```text
PlaymeshShortcutRegistry
  intent -> keyboard shortcuts
  intent -> Android TV key mapping
  shared Actions

PlaymeshFocusPolicy
  reading order
  directional traversal
  stable-id restoration
  scroll-to-focus
```

规则：

1. `MaterialApp` 根部注册平台级 Shortcuts/Actions；页面只声明意图和局部焦点关系，不重复判断 Android keyCode。
2. 全部自定义点击区域改为 `Button`、`InkWell + Focus` 或语义等价控件，同时实现 hover、focus、pressed、disabled。
3. Grid、Wrap 和响应式列表提供确定的二维方向焦点；布局列数变化后重新计算邻接关系，不能跳到不可见控件。
4. 所有异步列表使用稳定业务 ID 保存焦点。刷新后目标仍存在则恢复，已删除则移动到最近可用项或页面主操作。
5. ScrollView 在方向焦点越界时先滚动再移动焦点；焦点不得停留在屏幕外。
6. 仅触摸可见的手势操作必须增加菜单或按钮等键盘替代入口。

#### 游戏 WebView 平台工具

`GameToolDock` 必须显式管理 FocusNode：

1. 收起悬浮球可以通过 Tab、方向键或平台“打开游戏工具”意图获得焦点。
2. 激活悬浮球后展开工具条并聚焦第一个主要按钮；收起后焦点回到悬浮球。
3. 返回/关闭、刷新、二维码、性能、全屏、退出全屏、更多操作全部可用 Enter/Space/Select 激活。
4. 打开“更多”后聚焦第一项，方向键逐项移动；Escape/Back 关闭并返回“更多”按钮。
5. 二级信息、日志和编辑覆盖层使用焦点陷阱，关闭后回到原菜单项。
6. 关闭游戏前需要确认时，默认焦点放在非破坏性操作，不能因连续确认键直接退出。
7. 悬浮球拖动保留触摸/鼠标体验，同时提供可聚焦的“移动工具位置”命令完成遥控器移动。

WebView 内 SDK 注入工具以 `lib/core/game_sdk/features/game/` 的 Dart feature 为唯一手写源：

1. Shadow DOM 中所有操作使用原生 button/input，不用 click-only div。
2. 工具条和菜单实现 roving tabindex、方向键移动、Home/End、Enter/Space 激活和 Escape/Back 关闭。
3. 展开、关闭、信息、日志、清空、昵称编辑、保存和能力确认都具有 aria-label/label 与可见 focus-visible。
4. 菜单使用 `aria-expanded`、`aria-controls`、menu/menuitem 或等价语义；隐藏前若焦点位于内部，先归还触发控件。
5. 弹层打开时保存原 `document.activeElement`，关闭时恢复；不可把焦点丢到 body 或已隐藏按钮。
6. App 平台桥提供“聚焦平台工具”和“返回游戏内容”消息，只管理焦点，不改变游戏按键事件与业务协议。
7. 游戏作者自己的 HTML UI 不在平台强制改造范围，但默认游戏模板和 AI 提示词必须要求键盘/遥控器可操作。

#### Android TV 与设备适配

Android：

- Manifest 声明 `android.hardware.touchscreen` 非必需。
- TV 发行配置提供 Leanback launcher、横幅资源和遥控器导航入口；手机/平板 launcher 保持可用。
- Android TV Back/Menu/DPAD 映射到统一 Intent；不能直接把按键注入游戏脚本绕过平台焦点层。

响应式：

1. 使用 `LayoutBuilder`、约束和输入能力决定布局，不用设备型号判断。
2. TV 使用 10-foot 信息密度，主要文字、焦点轮廓和命中区在 720p 下仍清晰。
3. 平板支持横竖屏、触控加键盘，主从布局折叠时焦点顺序保持一致。
4. 手机支持最窄 320 dp、横屏低高度、刘海/圆角 SafeArea 和软键盘避让。
5. 电脑支持窗口连续缩放、鼠标悬停、Tab/方向键和高密度列表。
6. 文本缩放、国际化长文案和日夜主题必须与四类设备组合验证。

完成审计：

- 建立所有 App 路由、覆盖层和注入 UI 的可交互控件清单。
- 每个控件记录触摸、鼠标、键盘、Android TV 遥控器入口及焦点返回目标。
- 任一功能只能通过拖动、长按、hover 或触摸完成时，FR-24 视为未完成。

### FR-25 Authority SDK 打开分享界面与覆盖层默认关闭

公开 Game SDK：

```ts
interface PlaymeshAuthorityApi {
  /**
   * 打开当前 Authority 主机的 Playmesh 分享界面。
   * 只显示平台 UI，不向游戏返回分享 Token、URL 或二维码数据。
   */
  openSharePanel(): Promise<void>;
}
```

调用示例：

```js
shareButton.addEventListener("click", async () => {
  await playmesh.app.ui.openSharePanel();
});
```

调用链：

```text
playmesh.app.ui.openSharePanel()
  -> App SDK command
  -> AppWebViewBridge authority + runtime validation
  -> current GamePage.openSharePanel
  -> existing _openShare()
  -> existing _ShareOverlay
```

权限与安全：

1. SDK 先检查 `playmesh.main.session.isAuthority()`，宿主再根据当前运行连接独立复核 Authority，不能只信任 JavaScript。
2. 普通玩家、HTML 加入者、远程非 Authority App 和无会话页面返回 `not_authority`。
3. App 不在前台、GamePage 已销毁或当前运行实例不匹配时返回 `ui_unavailable`。
4. 调用必须发生在当前网页用户激活上下文中；无点击、键盘或遥控器激活时返回 `user_activation_required`，防止游戏循环弹出平台 UI。
5. 分享界面已打开时调用幂等，只聚焦现有界面；关闭后短时间重复请求受平台节流保护。
6. `openSharePanel()` 的返回值和错误不得包含 Share Token、读取 Token、上传密钥、URL
   或二维码内容；独立 `playmesh.app.lan.getShareLinks()` 只向 App-only 本机房主返回
   分享 URL/二维码，仍不得返回读取 Token、上传密钥或把原始凭据写进错误。

UI 与焦点：

1. SDK 入口直接调用现有 `_openShare()`，不展开 `GameToolDock`，不打开“更多”菜单。
2. 打开前保存 WebView 内触发元素；界面显示后默认焦点位于分享面板的关闭按钮或首个可用分享标签。
3. Android TV Back、Escape 或关闭按钮只关闭分享层；关闭完成后通知 SDK 恢复原网页元素焦点。
4. 加载、成功、失败、服务器选择和复制操作与悬浮工具入口完全一致。
5. SDK 请求与用户点击悬浮工具按钮同时发生时合并为同一个 `_ensureShare` 任务。

覆盖层初始化：

1. `GamePage`、`RemoteGamePage` 和相关游戏运行容器构造时全部可见状态显式初始化为 false。
2. 游戏 ID、运行实例、WebView 或页面 role 变化时重置覆盖层，不能继承前一个游戏状态。
3. WebView reload 后 SDK 注入工具回到收起状态，menu/info/log/edit/nickname 等面板全部隐藏。
4. 性能/FPS 显示不写入本地偏好，每次运行默认关闭。
5. 分享、调试和日志覆盖层不通过页面恢复、主题切换或设备旋转自动重新打开。
6. 初始只允许显示收起悬浮球；悬浮球本身继续支持键盘、遥控器、鼠标和触摸。

单一事实源与版本：

- 新方法在 `lib/core/game_sdk/features/game/` 的独立 feature 中声明 TypeScript、运行时片段和宿主执行器。
- 不直接修改 `assets/playmesh-library/sdk-src/` 或 `public/sdk/v1/` 生成物。
- Game SDK 以兼容新增规则递增 MINOR，并同步生成声明、Schema、补全、默认模板、AI 提示词和 `docs/game/sdk-v1.md`。
- Host command 必须加入 SDK 注册表、消费入口和单一源架构断言，不增加 GamePage 私有 JavaScript 旁路。

### FR-26 依赖驱动实施与去重

正式编码前从 FR 建立工作图，每个节点至少记录：

```text
owned files
single source
inputs
outputs
dependencies
version impact
targeted tests
final verification group
```

调度原则：

1. 编号不产生先后约束；无依赖的 Flutter、Go、SDK、Web 和文档工作可以交错推进。
2. 以 ownership 和事实源分批，同一个核心文件同一时间只归一个批次修改，减少冲突与覆盖。
3. 数据库 schema、Catalog 契约、SDK 注册表、国际化清单和主题令牌先形成稳定输出，再供多个消费端接入。
4. 生成物只在对应手写事实源达到本批次稳定点后统一生成和审阅。
5. 同一页面一次完成本轮已知的数据展示、视觉、国际化、主题、焦点和设备适配，不为每项需求重复拆装修复。
6. 同一 API/SDK 变化一次同步实现、Schema、文档、提示词、补全和测试，不保留跨批次临时双写。
7. 每批完成后运行其定向测试；多个批次汇合时运行契约测试；全部汇合后执行完整沙箱外回归。
8. 为避免重复而合并工作时，不得扩大事务、绕过权限检查、跳过中间失败用例或推迟安全验证。

建议优先识别的共享热点：

- `GamePage`、`GameToolDock`、WebView Bridge。
- `SdkFeatureRegistry`、Game SDK feature 和生成器。
- `GameLibraryRepository`、Catalog models/controller。
- go-server SQLite store、package service、Catalog handler。
- Developer Workspace HTML/CSS/JS。
- 国际化清单、主题令牌、构建脚本和版本日志。

实施计划每次因新增需求调整时，只重排受影响节点和下游验证；已经稳定且未受影响的批次不重复实现。

文件位置继续为：

```text
playmesh-library/cache/app/game-library.json
```

读取 API 从 `readLastOpenedAt()` 升级为 `readUsageStats()`；`GameSummary` 同时接收 `lastOpenedAt` 和 `launchCount`。原 `markOpened()` 升级为一次性更新两个字段的 `markLaunched()`，避免分两次写入造成时间与次数不一致。

### 5.5 go-server SQLite

新增或调整：

| 表/字段 | 用途 | 约束 |
| --- | --- | --- |
| `users` | 邮箱账号、密码哈希、显示名称、验证状态 | `normalized_email UNIQUE` |
| `user_sessions` | 用户门户会话 | 只存 `token_hash` |
| `email_verification_tokens` | 一次性邮箱验证 | 过期时间、使用时间、唯一哈希 |
| `upload_credentials` | 用户上传密钥 | `user_id UNIQUE`、`key_hmac UNIQUE` |
| `game_ownership` | gameId 所有权 | `package_id PRIMARY KEY`；最后一个版本删除后移除 |
| `games.owner_user_id` | 版本记录所属用户 | 外键到 users |
| `games.published` | 是否公开可见 | approved 后可切换 |
| `games.icon_path` | 根 icon.png 存储路径 | 可空 |
| `review_events` | 审核与用户操作审计 | 保留最小事件 |
| `server_settings` | 服务运行配置 | 增加 `allow_user_registration` 和 `require_email_verification` |

数据库版本策略：

1. 新 schema 使用独立版本号并要求全新数据库。
2. 检测到旧 schema 或缺少目标版本标记时拒绝启动，不执行自动 ALTER、数据转换或旧记录绑定。
3. 管理员需要先备份旧数据库和游戏包目录，再创建新数据库。
4. 新数据库不导入旧 approved、pending、rejected、匿名邮箱或 gameId 所有权记录。
5. 若业务仍需旧文件，管理员只能在新系统上线后使用新账号和新上传接口重新提交。

### 5.6 AI 默认提示词清单

`assets/playmesh-library/public/developer/prompts/manifest.json` 是模板元数据的唯一清单，`templates[].id` 是 AI operation 与本地覆盖文件使用的稳定键。

运行时模型：

```text
DeveloperAiPromptTemplateDescriptor
  id
  name
  category
  categoryName
  assetPath = promptsRoot + "/" + file
```

清单不手工保存正文摘要，避免每次调整正文还要同步修改哈希。构建器在每次打包时从当前文件自动计算摘要，并仅将摘要用于本次预检和产物复核。

App 本地 UI 偏好：

## 6. API 契约

### 6.1 Catalog `/apps/info`

Catalog API 目标版本固定为 `2.0.0`，不接受其他版本：

```json
{
  "catalogApiVersion": "2.0.0",
  "name": "Playmesh 公共游戏源",
  "author": "Example Studio",
  "homepage": "https://example.com",
  "supportsGameRelay": true,
  "relay": {},
  "userUpload": {
    "supported": true,
    "protocolVersion": "1.0.0",
    "path": "/api/user/uploads",
    "maxUploadBytes": 67108864
  }
}
```

### 6.2 Catalog 列表、图标和下载

```http
GET /apps/list?page=1&size=20&s_name=星海
Authorization: Bearer <read-token>
```

列表对每个 gameId 最多返回一条当前最新 approved 版本，并且仅在该版本 `published=true` 时返回。当前最新版本已下架时不回退到历史版本。Catalog 不负责返回本机启动次数；App 收到各源结果后使用本地 `GameLibraryUsageStats.launchCount` 计算热度并重新排序。

```http
GET /apps/download?id=com.example.game&version=2.0.0
GET /apps/icon?id=com.example.game&version=2.0.0
```

Catalog 2.0 下载必须指定版本；缺少 version 直接返回 400。指定版本必须等于该 gameId 当前公开最新版本，否则返回 `404 version_not_available`。不保留 Catalog 1.4 的“取最新版本”路径或历史版本下载路径。

### 6.3 用户认证

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/user/auth/captcha` | 获取图形验证码 |
| POST | `/api/user/auth/register` | 邮箱注册 |
| POST | `/api/user/auth/login` | 登录 |
| POST | `/api/user/auth/logout` | 退出 |
| GET | `/api/user/auth/verify-email?token=...` | 验证邮箱 |
| POST | `/api/user/auth/resend-verification` | 重发验证邮件 |
| GET | `/api/user/me` | 获取账号资料 |
| PATCH | `/api/user/me` | 修改展示名称 |

注册关闭时：

```http
POST /api/user/auth/register

HTTP/1.1 403 Forbidden
Content-Type: application/json

{
  "code": "registration_disabled",
  "message": "当前游戏源未开放用户注册"
}
```

`POST /api/user/auth/login`、邮箱验证和重发接口不受 `allowUserRegistration` 影响。登录页面不能依赖公共导航入口才能工作。

### 6.4 上传密钥和个人游戏

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| PUT | `/api/user/upload-key` | 创建、手填或轮换上传密钥 |
| GET | `/api/user/games` | 获取当前用户的游戏版本 |
| POST | `/api/user/games/:id/publish` | 上架已审核版本 |
| POST | `/api/user/games/:id/unpublish` | 下架已审核版本 |
| DELETE | `/api/user/games/:id` | 删除 pending、rejected 或 approved + unpublished；published 返回 409 |
| DELETE | `/api/user/games/by-package/:gameId` | 删除当前用户该 gameId 的全部已下架版本；存在上架版本时返回 409 |
| POST | `/api/user/uploads` | App 使用上传密钥提交审核 |
| POST | `/api/user/games/uploads` | 登录用户网页门户使用会话和 CSRF 上传 ZIP |

删除最后一个版本时，版本删除和 `game_ownership` 删除必须位于同一数据库事务；删除成功后其他账号可以重新上传并取得该 gameId。

两个上传入口共用同一校验服务和版本事务。版本冲突响应：

```json
{
  "code": "version_already_exists",
  "message": "该版本已存在，请提高 main.json.version",
  "currentHighestVersion": "2.3.1"
}
```

低版本使用 `version_must_increase`；非法三段式版本使用 `invalid_version`。所有权冲突优先返回 `game_ownership_conflict`，且不返回其他账号的最高版本。

### 6.5 管理员游戏上下架

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/admin/games/:id/publish` | 管理员上架当前最新 approved + unpublished 版本 |
| POST | `/api/admin/games/:id/unpublish` | 管理员下架任意 approved + published 版本 |

管理员接口使用现有管理员会话和 CSRF 防护。尝试上架历史 approved 版本返回 `409 not_latest_version`；pending、rejected、deleting 或已删除记录返回 `409 invalid_game_state`。

### 6.6 会话头像

建议参考昵称更新接口，在会话层增加平台私有入口：

```http
PUT /v1/sessions/{sessionId}/avatar
Authorization: Bearer <session-credential>
Content-Type: image/png
X-Playmesh-Avatar-Sha256: <hex>
```

行为：

1. go-core 根据凭据确定真实 Player。
2. 检查 Player 来源必须为 `lan_app`。
3. 相同摘要且文件存在时直接返回当前 Player。
4. 需要写入时通过平台私有控制通道交给权威 App。
5. 权威 App 校验并写入 `_sys-user-avatars/{playerId}.png`。
6. 成功后更新 `Player.avatar` 并广播完整会话快照。

返回：

```json
{
  "player": {
    "id": "u_123",
    "nickname": "林舟",
    "avatar": "/bucket/_sys-user-avatars/u_123.png",
    "connected": true
  },
  "session": {}
}
```

该接口只供 App 平台调用，不注入普通 HTML 游戏 SDK。

### 6.7 UI 国际化与 API 边界

所有 API 忽略 UI locale，不新增 `locale` 参数，也不因 Cookie、`Accept-Language` 或用户设置改变 JSON：

```http
GET /api/user/me
Accept-Language: en-US

GET /api/user/me
Accept-Language: zh-CN
```

在账号和数据状态相同的前提下，两次响应的字段、枚举、错误 code 和原始 message 必须一致。UI 只在渲染层使用错误 code、字段语义和本地词典生成展示文案。

### 6.8 Authority 平台 UI 命令

Game SDK 新增宿主命令：

```json
{
  "id": "request-id",
  "command": "authority.openSharePanel",
  "payload": {}
}
```

成功仅返回完成状态：

```json
{
  "id": "request-id",
  "ok": true,
  "result": null
}
```

错误 code 固定为 `not_authority`、`user_activation_required`、`ui_unavailable`、`rate_limited` 或通用桥接错误。该命令不属于 HTTP Catalog/Developer API，不新增服务器端点，也不返回任何分享数据。

## 7. 安全与可靠性

| 风险 | 控制 |
| --- | --- |
| 发行包携带旧提示词 | 构建前计算源文件摘要，构建后读取实际发行 Asset 复核；不一致即删除未发布产物并失败。 |
| 默认提示词多份副本漂移 | 仓库扫描只允许 `developer/prompts` 保存默认正文，运行时不提供硬编码回退。 |
| 语言配置缺失或回退成环 | 构建时校验清单、全部 key、文件路径和 fallback 有向图；非法时拒绝打包或启动。 |
| 词典注入 HTML/脚本 | 词典只接受受控 JSON 消息值，Web 默认以 textContent 渲染，禁止把翻译直接写入 innerHTML。 |
| 主题首帧闪烁 | Web 在主样式和应用启动前应用持久化主题；Flutter 在首个 MaterialApp 前加载 UI 偏好。 |
| 焦点丢失或困在 WebView | 统一平台快捷键、覆盖层焦点陷阱、关闭后恢复原触发点，并对 TV 方向导航做端到端测试。 |
| 游戏脚本循环弹出分享层 | Authority 双重校验、用户激活要求、幂等打开和关闭后节流。 |
| 分享信息意外泄露 | `openSharePanel()` 不返回数据；`getShareLinks()` 仅授权 App-only 本机房主并读取统一内存快照。平台不记录、不持久化、不在错误中回显 URL/token/PNG；游戏取得后的主动外传属于已接受能力边界。 |
| Token 出现在源链接 | 访问日志脱敏 `token` 查询参数；页面使用 `Referrer-Policy: no-referrer`。 |
| 上传密钥泄露 | HMAC + Pepper；不回显；不进入二维码、日志和工作区 JS。 |
| 账号撞库 | 高成本密码哈希、Captcha、登录限流、统一错误。 |
| 邮箱枚举 | 注册和重发返回统一状态。 |
| gameId 抢占 | 新数据库内使用所有权事务；冲突时不产生文件或记录。 |
| ZIP 或图片炸弹 | 大小、展开量、文件数、路径和图片尺寸限制。 |
| 远程图标跟踪 | 只接受与源 Host 同源的 URL。 |
| 头像身份伪造 | 会话凭据决定 playerId，忽略客户端目标文件名。 |
| 头像恶意文件 | App 规范化，权威主机再次验证。 |
| 头像缓存陈旧 | 固定路径使用 ETag 和 no-cache。 |
| 头像文件累积 | 会话开始清理遗留，结束清理保留 Bucket。 |
| 本地统计损坏 | 宽松解析并忽略非法记录；原子替换写入；保留上一份有效文件。 |
| 启动次数溢出 | 使用 JSON 安全整数上限并饱和递增，不允许溢出或归零。 |
| 扩展统计无限增长 | 2048 条、单项 16 KiB、总文件 4 MiB 三层限制和最旧优先淘汰。 |
| 关闭注册仅隐藏 UI | 注册 API 独立检查服务端开关并返回 403；不能依赖前端隐藏保障。 |
| 分享临时文件累积 | 专用目录、分享前清理、完成后清理、启动清理。 |
| 部分源故障 | 首页按源隔离，发布按源返回，不全局失败。 |

## 9. 测试与验收

### 9.1 在线源与下载

- 首页为每个 `showOnHome` 源保留区域。
- 空源和错误源不被过滤。
- 首页跨源同 ID 不去重。
- 搜索中相同 `gameId + 发布者` 只显示一个摘要，版本页和源页能还原该组全部 offer。
- 相同 gameId、不同发布者必须显示多个摘要，且各自只包含对应发布者的版本和下载源。
- 一级搜索摘要显示本机启动次数，并严格按 launchCount 倒序排列。
- 同一 gameId 的不同发布者摘要共享同一条本机使用统计。
- 热度相同时按最近打开时间、最高语义版本、名称和 groupKey 稳定排序。
- v1 最近打开文件被隔离，不读取旧时间；新 v2 统计从空记录开始。
- 每次实际进入游戏只增加一次；刷新、重连和页面重建不重复增加。
- 2048 条、单项 16 KiB、总文件 4 MiB 限制和最旧优先清理正确执行。
- 游戏详情在同一信息区域展示最近打开和启动次数；本地与在线搜索都按启动次数排序。
- 每源独立分页，不漏项。
- 下载任务键包含源、gameId 和版本。
- 本地和在线图标在成功、404、损坏和超限时正确处理。
- 同一源同一 gameId 无论存在多少历史记录，列表最多返回当前最新 approved 版本一条。
- 当前最新 approved 版本下架后，该源不返回该 gameId，且不回退到旧版本。
- 历史版本的下载和图标接口返回 `404 version_not_available`。
- 每次进入本地游戏库都在后台检查更新，不阻塞首屏且同一页面生命周期内不重复发起。
- 更新只匹配相同 gameId 和相同发布者；版本相同、版本较低或发布者不同都不提示。
- 快速升级列出目标版本及全部可用源，成功后保留游戏数据、启动次数和最近打开时间。

### 9.2 本地游戏库搜索

- 页面只存在一个搜索输入，发布者、名称、gameId、描述、版本和标签没有独立输入框。
- 空查询返回完整列表；清除按钮、Enter 和 `Ctrl/Cmd + F` 行为正确。
- 中文子串、拉丁字符大小写、首尾/连续空白和多个关键词 AND 匹配正确。
- 多个关键词可以分别命中名称和发布者等不同字段。
- 搜索结果按 launchCount、最近打开、语义版本、名称和 gameId 稳定排序。
- 输入防抖期间扫描、导入、升级或删除不会造成旧结果覆盖新 revision。
- 查询不发起 Catalog 请求、不修改统计、不触发扫描和更新检查。
- 无结果、游戏库为空、Manifest 部分损坏和超长文案均有稳定布局。

### 9.3 源导入

- HTTP/HTTPS、空或非空 Token。
- 非法 Host、userInfo、fragment、未知 query。
- `/apps/info` 401、500、超时、坏 JSON、版本不兼容。
- Catalog 1.4、旧 playmesh URI 和分离 Host/Token 输入全部明确拒绝。
- formatVersion 1 源配置被隔离，不转换任何源或 Token。
- 所有失败场景不落库、不覆盖原配置。
- 扫码与手工输入结果完全一致。

### 9.4 用户和发布

- 邮箱规范化唯一。
- 注册成功后的展示名称默认等于邮箱账号，修改前所有发布者展示使用该默认值。
- 开启和关闭邮箱验证。
- 未验证账号禁止登录。
- 验证 Token 一次性、过期和重发限流。
- 上传密钥复杂度、轮换失效、日志不泄露。
- 同 IP 30 秒限制在读取大请求体前执行。
- 当前 owner 上传新版本成功。
- 工作区和网页门户上传相同版本均返回 `409 version_already_exists`，不产生文件或审核记录。
- 工作区和网页门户上传更低版本均返回 `409 version_must_increase`，响应包含当前最高版本。
- pending、approved、unpublished 和 rejected 都阻止相同或更低版本再次上传；物理删除记录后不再参与比较。
- `1.2`、`v1.2.3`、`1.2.3-beta`、带前导零和其他非三段式版本都在客户端校验与服务端校验中被拒绝。
- 其他账号上传同 ID 返回 409 且无残留。
- pending 删除物理清理。
- approved + published 不能直接删除；所有者下架后可删除版本和包文件。
- 管理员和所有者都能对 approved 版本上下架，且共用同一状态服务。
- 删除最后一个版本同时释放 gameId；其他账号随后可重新声明。
- 包内 author 被账号展示名称覆盖。
- Catalog 只返回 approved + published。
- 关闭注册时公共导航隐藏登录/注册，直接访问 `/login` 仍可正常登录。
- 关闭注册时 `/register` 显示禁用状态，注册 API 返回 403 且无用户、Token、会话或邮件副作用。
- 已注册用户和待验证用户在注册关闭后仍能登录或完成邮箱验证。
- 发布弹窗只出现已启用、支持用户上传且已配置上传密钥的源。
- 不满足任一发布条件的源完全不显示；无合格源时显示前往配置的空状态。
- App 自身源的链接和二维码均为 `publicURL?token=...` 且内容完全一致。
- App 自身源声明 `userUpload.supported=false`，只读 Token 只能执行列表、图标和下载。
- 其他 App 可通过统一单输入框导入 App 自身源，发布弹窗不会显示该源。
- go-server 使用旧 schema 启动时立即失败，不修改旧数据库和包文件。

### 9.5 导出

- 文件名正确。
- 禁止字符正确清理。
- 连续分享 20 次不累积旧文件。
- 取消、失败、重启都能回收。
- 流式导出内存不随次数增长。

### 9.6 头像与 SDK

- 选择、裁剪、规范化、保存和恢复默认。
- 旧 profile 被隔离，新 profile 使用默认头像且不读取 avatarLabel。
- App 主机自己的头像可写入。
- App 玩家加入和重连同步成功。
- 相同摘要不重复上传。
- 伪造 playerId、HTML source、错误凭据被拒绝。
- 超限、非 PNG、错误尺寸被拒绝。
- 同步失败不阻止入局。
- 固定 URL 更新后 ETag 和内容同步更新。
- 会话结束清理 `_sys-user-avatars`。
- 普通 Bucket SDK 行为保持不变。
- `getCurrent`、`session.players`、所有玩家事件和 `members` 都返回一致 `avatar`。
- HTML 玩家 `avatar=null`，`setNickname` 保持原行为。

### 9.7 AI 默认提示词与发行构建

- `manifest.json` 中 ID、文件名唯一，所有登记模板存在、非空且为合法 UTF-8。
- 目录内每个业务 `.txt` 都被清单登记，孤立文件使测试和构建失败。
- Dart、JavaScript 和其他 Asset 中不存在默认提示词正文副本或硬编码回退。
- 所有 AI operation 通过同一 Template Store 读取默认模板。
- 本地自定义优先于默认模板；恢复默认后逐字返回当前安装包内模板。
- 修改任一模板而不改代码后，Windows、APK 和 HAP 发行 Asset 摘要随之变化。
- 构建前源摘要和构建后安装包 Asset 摘要逐项相同；缺失或不一致时构建失败且不保留可发布产物。
- SDK 生成不得改写提示词；项目提示词在请求时附加当前两份完整声明文件。

### 9.8 UI、国际化与主题

- App 首页在桌面、平板和移动端都严格按本地游戏库、在线游戏库、其他入口排序。
- 首页重排前后的路由、回调、返回值和业务请求序列完全一致。
- Developer Workspace 的保存、运行、发布、AI、更多菜单、三栏和移动三视图功能不变。
- Flutter 与 Web 在 320 px 到宽桌面范围无非预期横向滚动、重叠或文字溢出。
- 键盘可操作全部命令，焦点清晰；图标按钮、表单、状态和图片满足可访问性要求。
- 亮色、暗色和高对比内容截图通过视觉回归；reduced motion 下无非必要动画。
- 语言选择器完全由清单生成；新增测试语言只增加配置和词典即可出现，不修改代码。
- 缺 key、未知 locale、fallback 环、孤立词典和非法词典值都使构建或 go-server 启动失败。
- App、Developer Workspace 和 go-server Web 切换语言后，静态 UI、日期、数字和复数即时更新。
- 系统、日间和夜间三种模式切换正确，系统模式响应操作系统变化，用户固定模式不被覆盖。
- Web 首帧无错误语言或主题闪烁，二维码在所有主题下保持可扫描。
- 同一 API 请求在不同 UI locale 和主题下返回完全相同的 JSON 契约与机器码。
- API code 有词典映射时显示本地化文案，无映射时安全显示原始 message。

### 9.9 四类设备与键盘、Android TV

- App 全部路由、按钮、输入框、菜单、对话框、抽屉、底部弹层、列表项和分页控件都可仅用键盘完成操作。
- Android TV 仅使用方向键、确认键、返回键和菜单键即可完成本地游戏库、在线游戏库、设置、联机、开发者入口及返回首页的完整流程。
- 游戏 WebView 内的平台关闭按钮、收起状态悬浮球、展开菜单及其中全部选项均可获得焦点并通过键盘或遥控器触发。
- Flutter 页面、平台覆盖层、Shadow DOM 和 WebView 之间的焦点进入、焦点陷阱、关闭恢复及返回键优先级正确。
- 悬浮球支持键盘移动模式；移动时不误触菜单，确认保存位置，取消恢复原位置。
- TV 720p/1080p、平板横竖屏、手机 320 dp 和低高度横屏、电脑窗口缩放均无溢出、遮挡或焦点丢失。
- 在亮色、暗色、不同 locale 和系统大字体组合下执行导航矩阵，焦点环始终可见且不被裁切。
- 自动化扫描和人工验收均不得发现只能触摸或只能鼠标操作的平台 UI。
- Android TV 发行包声明 Leanback 能力，触摸屏不是必需特性；非 TV 平台安装和输入行为不受影响。

### 9.10 Authority 分享与覆盖层初始状态

- Authority 客户端调用 `playmesh.app.ui.openSharePanel()` 后打开与平台菜单完全相同的现有分享界面。
- 非权威主机、缺少有效用户激活、后台页面和平台 UI 不可用时返回规定错误，且不打开任何界面。
- `openSharePanel()` Promise 只表示界面是否成功打开，不返回 Token、链接、二维码内容或
  其他分享凭据；`getShareLinks()` 是独立的 App-only 本机房主读取授权。
- 连续快速调用执行幂等或限流，不叠加多个分享界面，不造成焦点混乱。
- SDK 打开分享界面时不连带展开工具菜单、FPS、详情、日志或调试覆盖层。
- 新开游戏、刷新、重连、切换游戏和角色变化后，除收起状态悬浮球外，FPS、菜单列表、分享、详情、日志和调试面板默认均为关闭。
- 分享界面按返回键或 Escape 关闭后，焦点恢复到调用前的游戏元素；无可恢复元素时回到平台悬浮球。
- 游戏脚本不能通过 DOM、日志、异常对象或未授权 SDK 旁路读取分享凭据；当前本机
  Authority/standalone host 可通过 `playmesh.app.lan.getShareLinks()` 取得统一快照，
  平台不得自动记录或持久化返回值。

### 9.11 沙箱外完整验证门禁

- 所有正式格式化、静态分析、单元测试、Widget 测试、浏览器测试、集成测试、打包测试和发行构建都必须先申请沙箱外执行权限。
- Flutter/Dart 命令使用开发文档规定的固定绝对 SDK 路径，并串行执行，禁止同时启动多个 Flutter 工具进程。
- 每个功能先运行最小定向测试，再运行所属组件全量测试、跨端契约测试和仓库全量回归；定向通过不能替代完整回归。
- 每项功能至少覆盖一个成功路径和一个失败路径；缺陷修复先加入可复现失败的测试。
- Windows、APK、HAP 等发行构建是独立审批步骤，不因测试已获准而默认获得构建许可。
- 每次正式验证把实际命令、环境、提交、开始与结束时间、退出码和结果写入 `docs/verification/`。
- 用户未授权、环境不可用或命令未执行时只能记录为“未执行”，不得写成“通过”。
- 完成判定同时要求代码、边界处理、测试、日志、文档、版本影响和已知限制闭环。

## 10. 推荐依赖链与合并批次（非执行顺序）

需求编号只用于追踪，不代表执行先后。实现者应先建立依赖图，再按共享数据结构、接口、生成器和文件所有权合并改动；满足依赖的批次可串行或并行推进，不必从 FR-01 顺序执行到 FR-26。

核心依赖关系：

```text
开发文档与版本门禁
  -> Catalog / 源配置 / 语义版本 / 本地统计 / SQLite 契约
     -> 游戏库与发布治理
     -> go-server 用户、门户与上传
     -> SDK、联机头像与 Authority 平台命令
  -> UI 结构冻结清单
     -> App / Developer Workspace / go-server Web 视觉重设计
     -> 可配置国际化、主题、键盘与 TV 适配
各功能批次 -> SDK/声明生成 -> 定向测试 -> 组件全量测试
全部批次收敛 -> 沙箱外全量回归 -> 独立审批的发行构建
```

| 合并批次 | 集中处理内容 | 进入条件 | 完成出口 |
| --- | --- | --- | --- |
| 文档与版本基线 | 开发规范、破坏性版本、验证模板、旧格式拒绝策略 | 无 | 约束与版本影响已记录 |
| 契约与数据底座 | Catalog 2.0、源配置 v2、三段语义版本、使用统计 v2、SQLite schema、所有权事务 | 基线完成 | 契约测试和迁移拒绝测试通过 |
| Catalog 与游戏库 | 本地搜索、按源首页、聚合搜索、每源最新版本、热度、源详情、图标、更新检查和快速升级 | 数据契约稳定 | App 定向与组件测试通过 |
| go-server 用户与发布 | 注册开关、邮箱验证、展示名称、上传密钥、限流、所有权、审核、上下架和删除 | SQLite 与 Catalog 契约稳定 | Go 全量测试和接口契约通过 |
| SDK 与游戏运行时 | 保留 Bucket、玩家头像、`avatar` 字段、Authority 分享命令、覆盖层默认状态、生成物 | 平台命令和玩家契约稳定 | SDK 生成一次，浏览器与 App 契约测试通过 |
| 导出与提示词发行 | ZIP 命名清理、提示词清单、Asset 摘要和包后复核 | 语义版本和发行规则稳定 | 打包测试通过，正式发行构建尚未执行 |
| UI 与多设备 | 首页优先级、App/Workspace/go-server Web 重设计、可配置 i18n、主题、焦点和 Android TV | 业务交互与 DOM/路由冻结清单完成 | 四类设备矩阵及视觉回归通过 |
| 收敛与发行 | 生成物一致性、全仓回归、真实网络、设备和发行包验证 | 所有功能批次完成 | 沙箱外验证记录完整，可发布 |

调度规则：

- 同一 schema、模型、生成器或共享文件涉及的需求尽量在一个批次一次修改，避免重复迁移、重复生成和反复适配。
- 不为过渡方便引入会立即删除的双契约、兼容层或临时字段；本轮允许破坏性更新。
- 独立模块在契约稳定后可以并行；共享文件必须明确单一负责人并在合并前处理交叉影响。
- 每个批次完成即运行对应定向和组件测试，不把所有验证积压到最后。
- 全量回归和正式构建在功能收敛后统一进行一次；失败项按依赖回到对应批次修复，不按 FR 编号返工。
- AI 提示词、SDK 和声明文件在所有相关源修改完成后统一生成，正式打包前再次校验最新状态。
