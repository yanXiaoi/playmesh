# Playmesh 5.0.1 更新日志

- 日期：2026-08-26
- App：`5.0.1+36`
- Runtime：`2.0.1+9`
- 状态：代码与自动化验证继续更新；Runtime 三端固定底包与 Linux Go Server 包已按当前
  源码重建并更新真实哈希；主 App 尚未打包或发布，Windows 光标、跨设备、长时在线与公网
  TURN 手工验收尚未执行
- 最新正式发行：`4.5.0+33`

## 升级原因

首页扫码原先直接创建邀请预检器，却没有向 Relay 4 客户端传入当前 Go Core 控制地址。
Relay 邀请因此先产生“当前加入入口没有可用的 Go Core”，随后又被加入协调层统一改写为
“请输入有效的 Playmesh 对局链接”。“加入对局”页的扫码入口另有一份流程，两个入口存在
继续分叉的风险。Runtime 源码虽已接入新 Relay，会随固定底包分发的 Android 与 Windows
制品仍可能落后于当前实现。

后续真机复核又发现：首页扫码页退出后，会先在可交互的首页等待邀请网络准备，直到准备完成
才进入带加载状态的远程页面；“加入对局”页的手工输入则已经在点击时立即显示遮罩，两者不是
同一个界面时序问题。审计还确认 Relay 成功准备会先建立会话、兑换并校验邀请，随后关闭会话，
远程页面又建立第二个会话；直接删除准备会同时删除受控入口、`gameId/gameName` 与 SDK
`expectedGameId` 隔离，因此本次保留校验并改为移交成功会话，而不是跳过校验。

首次跨设备复核还发现，后台预检虽然成功，但其邀请 POST 得到的 HttpOnly Cookie 只保存在
Dart HTTP 客户端中，不能自动进入手机 WebView 的 Cookie 仓库。此前直接导航到预检返回的
`entry`，会让刚生成的 Relay 二维码和 LAN 链接都立即收到 Authority 原样返回的“分享链接已
失效”。修复后仍复用预检建立的同一 Relay 会话，但 WebView 必须从本机 tunnel 的原邀请入口
完成自己的换票；LAN 使用相同规则。

长时分享审计进一步确认 `relay.tunnelTTLSeconds=21600` 同时被服务端和 Authority Go Core
当作隧道硬寿命，导致主机仍显示连接时，约 6 小时后的原二维码和原链接一起失败。这个值
不能只增大：TURN REST 凭据仍会过期。修复后在线租约由主机信令连接持有，每次加入重新签发
匹配两端的短期 ICE/TURN 凭据；主机断开或停止分享才撤销原邀请。

真机复核还确认过一种相反假象：加入端已经成功进入 Core Session，服务端再次使用同一玩家
身份会返回 `409 player_connected`，但主机已经打开的“房间”页仍停留在旧快照，继续把该玩家
显示为已断开。原因不是 Relay 没有加入，而是主 App 只在 LAN 在线人数投影变化时重建分享
面板，Runtime 更只在打开面板时读取一次成员。现在两端都跟随每个 Session 成员快照刷新，
即使人数没变，只更新昵称、在线状态或 `lan/direct/relay` 连接方式也会立即重建。

Windows 窗口模式审计同时确认，组合模式 WebView 只转发鼠标 `MOVE`，没有按 WebView2
要求在鼠标离开纹理时发送 `LEAVE`。WebView2 因而可能继续认为指针停留在旧网页区域，
非全屏下重新进入游戏内容时不再产生新的 `CursorChanged`，使 Flutter 保留普通箭头。
本次补齐进入/离开边界，并在新文档加载时恢复默认光标；不保存跨文档或跨游戏光标缓存。

本次是兼容修复：邀请 URL、Relay 4 wire 契约与公开 SDK API 均不改变，因此 App、Runtime
及行为发生变化的 Go Core 递增 PATCH；Core 协议、Game SDK、App Bridge SDK、Catalog API
与 Relay 协议不因该修复额外升版。

## 用户变化

- App 本地游戏 WebView 可按项目开启跨源隔离响应头；默认关闭以兼容现有游戏。开启且
  WebView 支持该能力时，游戏可以启用 `SharedArrayBuffer`/WASM 线程，不支持时仍由游戏
  使用单线程路径。
- Windows 窗口模式下，游戏网页在指定区域使用 `cursor: none` 时可以实时隐藏鼠标，不再
  依赖进入全屏触发重新同步；鼠标离开游戏区域或切换游戏后恢复由当前页面重新决定。
- 首页扫码和“加入对局”页扫码都调用同一个二维码采集方法，并与手工输入共同进入唯一的邀请
  准备方法；扫码页面只负责读取二维码，不再自行持有身份、Core、发现服务或导航逻辑。
- 手工输入继续兼容严格受控的 LAN `/playmesh/join#inviteToken=...` 和 Relay `/j/...`
  链接。从释放发现租约、预检邀请到导航完成，加入页显示阻止操作与返回的全页“正在加入”
  遮罩，不再在页面无反馈的情况下等待。
- 首页和“加入对局”页扫码在二维码返回后的第一帧先显示根级“正在加入”遮罩，至少完成一帧
  绘制后才开始邀请网络准备；遮罩阻止触摸和系统返回。手工输入仍在点击加入时立即进入同一
  视觉状态，没有额外等待扫码层。
- Relay 邀请仍执行有效性、受控入口和游戏身份校验，成功后把同一个已建立会话交给远程页面
  继续使用，不再关闭后重建。Dart 预检与 WebView 是不同 Cookie 仓库；LAN 与 Relay 都由
  WebView 通过同一本机 tunnel 的原邀请入口建立自己的 HttpOnly Cookie，再重定向到已经
  校验的 `entry`，不能把预检 Cookie 当成可移交的浏览器登录态。
- 公网分享的二维码和复制链接现在拥有相同的在线租约：主机信令持续连接时不再因创建时间
  达到 6 小时而失效；主机断开、主动停止分享或服务端心跳确认失联后，两者同时失效，下一次
  分享重新生成新的二维码和链接。
- 两个入口都在每次实际加入时读取当前 Go Core 地址。Core 尚未启动、地址未就绪、Relay
  建链失败或邀请响应异常时，不再一律显示“无效链接”。
- 加入失败界面在本地化说明之外，原样显示稳定错误 code、运行时类型、原始消息、完整
  cause 链和可用堆栈。邀请 URL、内部 URL、Token、共享密钥与二维码 Data URL 会明确显示为
  `[REDACTED ...]`，其余业务原因不删除。
- 首页使用可滚动、可选择的错误对话框；“加入对局”页在原位置显示同一格式的完整诊断。
- 主 App 与 Runtime 已经打开的“房间”页实时跟随 Core Session 成员快照；成功中转加入后不再
  因旧 UI 快照继续显示为“已断开”，昵称和“局域网/直连/中转”方式变化也会即时显示。

## 实现与边界

- `GameAssetGateway` 在任何路由处理前读取不透明的可选 `main.json.config`；只有公共读取器
  得到 `webRuntime.multithreading == true` 时，才统一设置
  `Cross-Origin-Opener-Policy: same-origin` 与
  `Cross-Origin-Embedder-Policy: require-corp`，覆盖入口、平台资源、游戏资源、Bucket 和
  错误响应。缺失、`false` 或错误类型保持原有响应；普通浏览器分享网关不参与该策略。
- vendored `webview_flutter_windows` 在 Flutter `MouseRegion` 进入时发送当前坐标 `MOVE`，
  离开时经平台通道调用原生 `SetCursorLeave()` 并发送
  `COREWEBVIEW2_MOUSE_EVENT_KIND_LEAVE`；导航开始时只广播一次普通箭头复位，之后仍由当前
  WebView2 `CursorChanged` 决定显示，不新增控制器级光标缓存。
- `GameInvitationScannerPage` 是纯二维码采集页面；`scanAndPrepareGameInvitation` 是两个 App
  扫码入口唯一的采集链路，扫码和手工输入再共同调用 `prepareGameInvitation`，最终仍进入
  `GameJoinPreparationService.prepareLink()`。
- `DefaultGameInvitationInspector` 支持动态 Core 地址提供器，Relay 预检在操作发生时求值，
  避免 App 启动期间端口变化造成陈旧地址。
- `InspectedGameInvitation` 与 `RemoteGameLaunch` 以单次 take 语义移交 Relay 会话和受控
  `entry`；Coordinator 在取消、`gameId` 不匹配和其他校验失败时关闭未移交会话，App Router、
  RemoteGamePage 与 Runtime 导航接管成功会话，并在导航失败、页面退出或 Runtime 关闭时
  回收。连接资源不会经公开 SDK 或游戏脚本暴露。
- `GameInvitationInspectionException`、`GameJoinException`、App SDK 命令错误与 Runtime LAN
  错误保留 cause、cause stack 和非敏感上下文；App、App Bridge 与 Runtime 共用同样的诊断
  格式与脱敏规则。
- App SDK 与 Runtime SDK 的链接加入、扫码加入在后端共同进入
  `GameJoinCoordinator.prepareLink()`；这里只做可信用户操作、gameId、自邀请和取消边界，
  不执行仅属于发布/读取分享信息的 Authority 鉴权，也不提前执行 Core 会话鉴权。
- 主 App 的 `GameShareCoordinator` 对每个 Session 快照发布状态以驱动已打开的分享面板；
  LAN presence 仍只在实际值变化时防抖发布。Runtime 分享对话框在可见期间订阅同一类 Session
  消息，并在关闭时取消订阅，快速关闭也不会留下监听。
- Relay Host 建立 peer 失败时通过仅允许 Host 发送的 `peer.error` 把原始原因返回加入端；
  ICE 超时诊断包含连接/收集状态、候选类型和已脱敏的 ICE URL，不记录 TURN 用户名、密码、
  邀请或共享密钥。部署时不按公网/私网地址性质拒绝启动，错误地址仍由运行时连通性和诊断暴露。
- 邀请结构、凭据和 Authority 校验保持不变；仅取消 `expiresAt` 对在线邀请的本地硬淘汰，
  实际有效性改由服务端 tunnel capability 与在线主机租约决定。完整邀请仍不会写入日志或界面。

## 已知限制与未执行项

- 本轮已执行 Windows 固定底包构建，但没有执行真实窗口手工验收；发布前仍须复核窗口/全屏
  光标切换、LAN/Relay 邀请换票和页面刷新。构建成功不能替代 WebView2 真机行为验证。
- Relay 4 邀请中的 `expiresAt` 作为 wire 兼容字段保留，但不再单独淘汰在线主机的二维码或
  链接；服务端已撤销、主机已断开或停止分享的邀请仍不能重新使用。
- 尚未使用两台真实设备执行“电脑经公网 TURN 分享 → 手机两个扫码入口分别加入”的验收，
  也未完成超过 6 小时的真实在线老化测试，因此二维码相机权限、运营网络、NAT、TURN 端口、
  心跳检测和服务端部署仍是独立变量。
- 自动化证明不再重复创建成功 Relay 会话；后台身份预检和 WebView Cookie 建立会各执行一次
  邀请 POST，因为二者属于隔离的 HTTP 客户端。自动化没有给出公网环境的固定耗时；DNS、
  信令、ICE/TURN 和 Authority 响应仍决定首次准备时间，必须用真机日志分别测量。
- Runtime Windows 固定包已构建并检查，但主 App Windows/Android 发布包未构建；源码与底包
  通过不等于商店签名、安装升级或真实 WebView 行为已验证。
- 该修复必须部署新的 Go Server，并让加入端使用带 Go Core `0.6.1` 的 App/Runtime。升级
  服务端会丢失内存中的现有 tunnel，部署当次必须由主机重新分享；部署完成后的邀请才遵循
  在线租约语义。旧加入端仍会按邀请中的历史 `expiresAt` 本地拒绝长时链接。

## 升级与回滚

- App 与 Runtime 应与 Relay 4 的 Go Core/Go Server 作为同组部署；不要把 Relay 3 固定底包
  与当前邀请混用。
- 回滚时同时恢复 App/Runtime 代码、三个固定底包及 `resources/runtime/update.json`，避免
  清单哈希与实际文件不一致。此次修改不迁移用户数据，回滚不需要清库。
