- `main.json.entries.game` must be explicitly declared and reference an existing complete HTML game entry. `single_screen_multiplayer` must explicitly declare `entries.controller`, and `multiplayer` must explicitly declare `authority.entry`. A leading segment named `app` is an ordinary user directory: `app/index.html` maps to physical `app/app/index.html` and runtime `/app/index.html`. [SDK AND CAPABILITIES]
- The complete `playmesh-main.d.ts` and `playmesh-app.d.ts` generated by the same SDK build appear below. They are the single source of truth for methods, parameters, return values, types, and versions. Never invent an undeclared member.
- `playmesh.main.storage.getBucket(name)` returns a Bucket. Keep JSON data private; uploaded files are read at runtime through the returned `/bucket/...` URL.
- Use `playmesh.main.binary` only for raw multiplayer `Uint8Array` communication; never create your own WebSocket.
- `playmesh.app` represents the current device identity and platform capabilities. After `playmesh.ready`, read state through `playmesh.app.capabilities.getRegistry/getDeclared/getAvailable`. Call `create(code, options)` only for a native-adapted capability whose descriptor exposes the required methods or events.
- The game project owns localization for its content and assets. The platform does not translate game DOM, player nicknames, tags, logs, or other dynamic content. To select the game's own language resources, call the read-only `playmesh.app.runtime.getLocale()` after `playmesh.ready`. In an App WebView it returns the language of the App displaying that page. In a regular browser it returns the browser system language and falls back to `zh` if detection fails. Never read the Authority host language or internal platform dictionaries.
- `playmesh.app.performance` reports only local FPS, Session RTT, and performance overlay state for the current client. Never use those telemetry values as Authority state, a win/loss decision, or another client's performance.
- Prefer standard Web APIs for non-sensitive capabilities such as accelerometer, gyroscope, and device orientation. User-triggered `<input type="file">` also requires no capability declaration. Optional package-root `capabilities.json` declares only sensitive permissions intercepted by the WebView (`media.camera`, `media.microphone`, `device.midi`) and Playmesh native-adapted capabilities such as `device.vibration` and `sensor.pose6d`. `required` belongs to the main page; `controllerRequired` belongs only to the single-screen multiplayer controller.
- After declaring camera, microphone, or MIDI, still use `getUserMedia()` or `requestMIDIAccess({sysex:true})` directly for capture/access. For native short-phrase speech recognition, create `media.microphone` from the live registry, call `toText({localeId,listenFor,pauseFor})`, and listen for `textOnSoundLevelChange` and `textOnResult`. Never invent methods absent from the descriptor, and handle denial and unsupported platforms.
- `device.vibration` uses the `vibration` plugin adapter. Create it from the live registry. `vibrate` accepts `duration/pattern/repeat/intensities/amplitude/sharpness/preset`; stop continuous or repeating vibration with `cancel`.
- Create `sensor.pose6d` only when the live registry reports it available. Read metric XYZ position, XYZW quaternion, and tracking state from `pose` events. Call `openVideo` only when video is actually needed, then pass the opaque source to `playmesh.app.media.open()` to obtain a `MediaStream`. Do not create WebRTC, media URLs, ports, or signaling servers. Close the `AppMediaSession` and capability instance afterward.
- `playmesh.app.ui` provides the unified centered game menu, sharing, logs, fullscreen, information, performance, and exit controls. A game-owned menu button may only call `showGameSidebar()` to open the unified menu; the compatibility method name does not mean the menu remains a sidebar. Do not call nonexistent `hideGameSidebar()` or `onMenuRequest`. Use `configure({fallbackUi:false})` only when the game fully implements replacement UI.
- The SDK provides communication, storage, platform capabilities, and controlled session-state transitions. Game Authority must decide readiness, countdown, start conditions, turns, victory, and completion. `session.start/finish` only request Core session-state changes and never implement game rules.
