[AGENT EXECUTION RULES]

3. A `dangerous=true` operation pauses and requests developer approval through the workspace. Approval resumes the original request, rejection returns 403, and no decision within 30 seconds returns 408. Never bypass approval by omitting or altering the AI channel header.

Declare capabilities only in sibling `capabilities.json`, and use only package-root `icon.png` as the library icon. Never generate removed fields.
5. Manage `capabilities.json` only through the project capabilities API. It declares only sensitive permissions intercepted by the WebView and Playmesh multi-platform adapted capabilities. Read the complete capability registry before adding or implementing a platform capability, and use the capability test API when diagnosing native adapters.

Use PUT for a complete save, PATCH for an exact edit, and prefer file-change preview plus atomic apply for multi-file changes.
7. Refresh the project tree after creating or deleting files or directories. Strictly limit deletion to the current project.
8. Run project validation when finished and fix every error. Start the project if it is not running; prefer restart when it is already running.
9. You do not need to keep an SSE connection open. Poll runtime status and read recent structured logs; use SSE for real-time events and approval notifications when needed.
10. Code must be complete and runnable. Do not use ellipses, TODOs, or pseudocode.

- `entries.game`, `entries.controller`, and `authority.entry` are relative to the outer physical `app/` and must not start with `/`. A leading segment named `app` is an ordinary user directory: `app/index.html` maps to physical `app/app/index.html` and runtime `/app/index.html`. Only `playmesh` and `bucket` are reserved first segments.

- Always `await playmesh.ready` before any SDK call.
- At the root, use only the aggregate `playmesh.ready` and the `playmesh.main` and `playmesh.app` partitions. Session, players, authoritative synchronization, lifecycle, and storage belong to `playmesh.main`. Current-client identity, device, capabilities, media, locale, performance, and UI belong to `playmesh.app`. Do not call removed root members such as `playmesh.session`, `playmesh.storage`, or `playmesh.runtime`.
- Never directly access PlaymeshBridge, `chrome.webview`, Core HTTP, WebSocket, internal tokens, player credentials, `data`, `cache`, or other game packages. Use `playmesh.main.binary` for binary communication and Bucket upload for runtime files.

[SDK AND CAPABILITIES]
- The `playmesh-main.d.ts` and `playmesh-app.d.ts` declarations below are the single source of truth for SDK interfaces. Never invent members.
- `playmesh.app` represents only current-device identity and hardware capabilities; it never replaces the authoritative Game SDK.
- The game project owns localization for its content. The platform does not translate game DOM, player nicknames, tags, or logs. After `playmesh.ready`, use read-only `playmesh.app.runtime.getLocale()` to select the game's own language resources. In an App WebView it returns the language of the App displaying that page. In a regular browser it returns the browser system language and falls back to `zh` if detection fails. Never read the Authority host language or internal platform dictionaries.
- `playmesh.app.performance` reports only local FPS, Session RTT, and performance overlay state for the current client. Never use those telemetry values as Authority state, a win/loss decision, or another client's performance.
- Use standard Web APIs directly for non-sensitive capabilities such as accelerometer, gyroscope, and device orientation. User-triggered `<input type="file">` requires no capability declaration. `capabilities.json` declares only sensitive WebView permissions (`media.camera`, `media.microphone`, `device.midi`) and native-adapted capabilities such as `device.vibration` and `sensor.pose6d`; each page uses only the capabilities declared for its own role.
- After declaring camera, microphone, or MIDI, use `getUserMedia()` or `requestMIDIAccess({sysex:true})` directly. For native short-phrase speech recognition, create `media.microphone` from the live registry, call `toText({localeId,listenFor,pauseFor})`, and listen for `textOnSoundLevelChange` and `textOnResult`. Call `playmesh.app.capabilities.create()` only when the descriptor exposes the required methods or events; never invent SDK methods.
- `device.vibration` uses the `vibration` plugin adapter. After creating an instance, `vibrate` accepts `duration/pattern/repeat/intensities/amplitude/sharpness/preset`. Stop continuous or repeating vibration with `cancel`.
- `sensor.pose6d` provides metric XYZ position and XYZW quaternion through `pose` events. Call `openVideo` only when video is needed and pass the opaque source to `playmesh.app.media.open()`. Do not create WebRTC, media URLs, ports, or signaling servers. Close the media session and capability instance afterward.
- `playmesh.app.ui` provides the unified centered game menu, sharing, logs, fullscreen, information, performance, and exit controls. A game-owned menu button may only call `showGameSidebar()` to open the unified menu; the compatibility method name does not mean the menu remains a sidebar. Do not call nonexistent `hideGameSidebar()` or `onMenuRequest`. Use `configure({fallbackUi:false})` only when the game fully implements replacement UI.
- The SDK does not decide game rules. Game Authority determines readiness, countdown, start, turns, victory, and completion. `session.start/finish` only ask Core to change the base session state.
